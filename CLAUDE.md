# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

All phases of the original plan are implemented and tested against the user's real config file: `model.py` (domain dataclasses), `parser.py` (XML → model), `exporter.py` (model → XML, byte-for-byte round-trip on the sample file), `validator.py` (structural + conflict checks), `catalog/` (channel/NOTE-CC/data1 → physical control name, see below — the user's real setup mixes DDJ-XP2 and XDJ-XZ in one config, so lookups always check every registered controller and can return ambiguous matches), `gui/` (PySide6 UI, see below). Root `main.py` is unrelated leftover PyCharm boilerplate, not part of the package. `library/` (see below) is a newer, separate initiative for managing the DJ's actual music collection rather than MIDI mappings.

### `catalog/` — plugin-style controller registry

`catalog.py` was split into a package: `catalog/_registry.py` (the `ControllerDefinition`/`ControlInfo` dataclasses and a plain-dict registry), one module per controller (`ddj_xp2.py`, `xdj_xz.py`), and `catalog/__init__.py` (imports each controller module for its registration side effect, re-exports the public API). Scope per controller is intentionally limited to discrete press/toggle controls (buttons, pad grids) — continuous controls (faders, TRIM/EQ knobs, jog wheels, touch strips/encoders) are left out since they're rarely remapped in Serato configs and don't reduce to one readable name.

**To add a new controller with official docs in hand**: write one new `catalog/<name>.py` module (static entries + a pad-grid function — use `_registry.make_sequential_pad_lookup(...)` if the note layout is simply `(pad-1) + mode_index*16`, otherwise write a bespoke one like `ddj_xp2.py`'s), end it with `register(ControllerDefinition(...))`, and import that module from `catalog/__init__.py`. Nothing else needs to change: `catalog.CONTROLLER_NAMES`/`PAD_COUNTS` are computed live from the registry on every access (module-level `__getattr__`, not a snapshot — a controller registered after the package is imported, e.g. interactively, is picked up immediately), and the Layout/By-Controller/Controller-Images tabs' combos all read from `CONTROLLER_NAMES` rather than a hardcoded list. Full docstring/steps in `catalog/__init__.py`; `tests/test_catalog_registry.py` exercises this end-to-end by registering a throwaway controller and checking it shows up in `lookup()` and `gui.layout.build_layout()`. See `~/.claude/plans/sprightly-questing-bengio.md` for the original phased plan (predates this package split).

**To add a controller with no official docs** (the original blocker for the user's Behringer CMD LC-1 and a "miniPad"): use the GUI's **Controller Setup** tab (see below) instead of transcribing a PDF by hand — it generates a `catalog/<slug>.py` module ready for the one manual import-line step above, either from live-learned MIDI or from an existing Serato XML's triggers.

### Empirical finding: the 10x duplication

In the user's real file, every unique `(channel, event_type, control)` trigger is repeated verbatim 10 times (64 unique triggers × 10 = 640 total `<control>` elements — confirmed via `build_mapping_groups`/`_check_duplicate_triggers`). This is **not** export bloat: the user confirmed deleting the "duplicates" breaks the config in Serato. The reason for exactly 10 is still unconfirmed (best guess: some internal Serato state not represented in this XML format, e.g. auto-loop length presets), but treat it as load-bearing. `validator.py` flags identical-content duplicates as `info`, explicitly saying not to deduplicate — never change that to `error`/cleanup advice without new evidence.

### GUI structure (`gui/`)

`left_tabs` has six tabs. The first three pair a tree (one resizable column per channel/deck/controller — implemented via `QSplitter(Horizontal)`, not a single nested tree) with a `layout_view.py` `ControllerLayoutView` DJ-oriented layout of the same underlying data. The renderer uses compact pad, button, knob, fader, and jog glyphs inferred from catalog vocabulary, with a generic fallback for unknown controls. For a controller with `gui/geometry.CONTROL_GEOMETRY`, the layout switches to real-position mode (markers at each control's true photographed coordinate; see the module docstring / TODO.md's DJ-layout-visual-fidelity chantier), and a per-view **"Controller photo"** checkbox (**on by default** as of `v0.47.56`; kept so it can be turned off) then draws the real reference photo behind those markers via `layout_view.draw_reference_photo()` — `ControllerEmulatorView` carries the same checkbox for `EmulatorLayoutView`, also on by default. No effect in the classic card-grid fallback (a controller with no geometry). Not persisted — the default reapplies each session.
- **By Channel**: `tree_model.build_channel_columns()` (one column per MIDI channel, each Note/Control → Control → UserIO → Mapping) + a plain `ControllerLayoutView` colored by which Serato deck(s) use each control.
- **By Deck**: `deck_tree.build_deck_columns()` (one column per Serato deck, each Slot → function) + `ControllerLayoutView(show_deck_filter=True)`, whose combo narrows the coloring to one selected deck.
- **By Controller**: `controller_tree.build_controller_columns()` (one column per controller — DDJ-XP2, XDJ-XZ — grouped by catalog section; sections with no used entries stay collapsed) + a third plain `ControllerLayoutView`. A leaf here can represent dozens of real `<control>` elements at once (a whole pad-mode grid cell), so clicking one reuses `MainWindow._on_layout_cell_activated` rather than feeding the edit panel directly.
- **Controller Images**: `controller_image_view.ControllerImageView` — a static, zoomable/pannable viewer (no data binding) for the official Pioneer controller diagrams in `controllers/<slug>/*.png` (one common directory, one subdirectory per controller holding everything for it — artwork and source PDF together, see `controllers/README.md`; a `controllers/custom/` subdirectory is reserved for Controller Setup exports — committed to the repo for personal/reference use only — the Pioneer/AlphaTheta ones are copyrighted images, not to be assumed clear for redistribution beyond that; as of `v0.47.95-controller-assets-reorg` this replaced the previous, split `assets/controllers/`/`docs/controllers/` layout, see that TODO.md entry — CLAUDE.md's and TODO.md's own older narrative below still describes files by their pre-reorg `assets/controllers/<slug>.png` paths, left as an accurate historical record rather than rewritten). Each controller bundles **two variants** under a `reference.png` (clean device render) / `reference-midi.png` (the same view with the MIDI Message List's callouts printed over it) naming convention, both inside that controller's own `controllers/<slug>/` directory — `controller_image_view.image_variants(reference_image)` resolves the pair from either name — and a **"MIDI info" checkbox** swaps between them (disabled when a controller only ships one variant, e.g. a Controller Setup attachment). The checkbox defaults to whichever variant that controller's `catalog` `reference_image` actually names, and once the user toggles it their choice is pinned across controller switches (`self._midi_override`). A "Show real layout" checkbox (the "DJ layout visual fidelity" chantier, issue #13) overlays colored markers directly on the image at each modeled control's true position, sourced from `gui/geometry.py`'s `CONTROL_GEOMETRY` — hand-measured `ControlGeometry(x, y, w, h, shape, color)` fractions of the reference image's full width/height, checked by cropping the region of the image each entry claims to describe. Decorative and read-only, same as the rest of this tab (no click handling, no binding to `MainWindow.config`): the checkbox is disabled with a tooltip when the selected controller has no entries in `CONTROL_GEOMETRY`, **and also whenever the on-screen variant isn't the one `reference_image` names** — `CONTROL_GEOMETRY`'s fractions only line up with the variant they were measured against (`_draw_geometry_overlay` double-gates on `isEnabled()` so a checked-but-disabled box never draws a misaligned overlay). - **Live Monitor**: `live_monitor.LiveMonitorView`, backed by `midi_io.py`. Watches real MIDI traffic and drives the same three `ControllerLayoutView`s (plus the Controller Images overlay and every open Controller Emulator dock) via `MainWindow._on_live_midi_event`, which does five independent things (issue #13 part 2): `_update_layout_selection` sets the persistent (until the next selection) red selection border; `flash_key(key)` briefly (220ms, `QTimer.singleShot`) turns a discrete pad/button glyph white to mimic it lighting up on a real hit; `set_value(key, event.data2)` records the live 7-bit value for a knob/fader glyph, rotating a knob's marker (-135 to +135 degrees, a typical pot sweep) or moving a fader's thumb within its track — a level, not a pulse, so it persists like a real control staying wherever it was left; and (since `v0.47.60`) `set_active(key, bool)` holds a steady **amber "held down" highlight** (`_ACTIVE_BORDER_PEN` border + translucent amber fill, the emulator's phase-5 toggle look) — lit on a live Note On (`data2 > 0`), cleared on Note Off / velocity-0. A release resolves against `"Note On"` too (catalog entries are all stored that way) so the selection/highlight tracks the just-released control instead of vanishing; a plain CC leaves held state alone; and set_active runs *before* flash_key so the 220ms white pulse always paints on top of the amber. Because a red selection border and the amber active border can't both show, selection wins the border and the amber *fill* keeps "held" visible underneath. That `set_active` path is the **input-direction** slice (Note On/Off = press/release). Since `v0.47.61` there is also an **output-direction** slice: `MidiEvent.direction == "out"` events (Serato → controller LED feedback, seen on the virtual monitor port `MidiMonitor.VIRTUAL_MONITOR_NAME`) are routed to `_on_output_led_event` *before* any of the above and drive `set_led(key/label, on)` on the same three `ControllerLayoutView`s, the Controller Images overlay, and every open emulator dock (`ControllerEmulatorView.set_led_from_hit`). The LED highlight is **latched** — lit on a Note On with velocity > 0, cleared on Note Off / velocity 0 — reuses the identical amber `_ACTIVE_BORDER_PEN` look, and lives in a `_led_keys`/`_led_labels` set **kept separate** from the input-direction `_active_keys` so an input-direction release can't clear an LED the software is still driving (rendered as `key in _active_keys or key in _led_keys`). Output-direction events do **not** flash, change the selection, or touch `set_value`; a CC on the output port is ignored (no LED meaning). The LED note number is **assumed equal to the input trigger note** — Serato's own convention for nearly every mapping, and there's no per-control `led_note` field in the catalog — so a controller that lights a different note than it sends won't resolve. **Jog-wheel rotation** does react, since `v0.47.62`: a jog turn is a stream of relative Control Change ticks that deliberately have *no* catalog entry (continuous controls are out of catalog scope), so `_on_live_midi_event` resolves it against `gui/jog.py`'s small per-controller table instead — **XDJ-XZ** (platter CC `0x22`/`0x29`, wheel-side CC `0x21`/`0x26`; decks 1/3 → left "Jog wheel", 2/4 → right-tray "Jog wheel (R)") and, **DDJ-1000** (`v0.47.64`, platter CC `0x21`/`0x29`/`0x1F`), **DDJ-FLX10** (`v0.47.65`, platter CC `0x22`/`0x23`/`0x29`/`0x1F` + wheel-side `0x21`/`0x26`) and **DDJ-REV1** (`v0.47.66`, same as FLX10 minus `0x29`) — all 2-deck, all schematics draw only the left deck so every deck channel resolves to their one "Jog wheel". All on the deck channel with the same `0x40`-centred relative encoding read from each controller's MIDI Message List rendered table. Many of these CCs collide (e.g. `0x21` is used by all four on the deck channel), so `jog_cell_keys_for_event` returns *every* matching marker and each view spins only the controller it shows. Single-jog controllers are a `(data1 set, key)` table in `gui/jog.py`; XDJ-XZ is the one special case, resolved side-aware by deck channel. `_on_live_midi_event` decodes the signed delta (`decode_jog_delta`), and integrates it into each jog glyph's notch angle via `ControllerLayoutView.spin_jog` / `EmulatorLayoutView.spin_jog` (a running 0–360° accumulator in `_jog_angles`, `_JOG_DEGREES_PER_TICK = 6.0` — a cosmetic gain, not the platter's real ~1440-tick/rev resolution). The jog branch runs *before* `_update_layout_selection` and early-returns, so a jog turn never flashes, moves the red selection, or touches `set_value`; deck 1/3 → the left "Jog wheel" cell, deck 2/4 → the right-tray "Jog wheel (R)" cell (same split as the pad grids). Since `v0.47.63` the Controller Images overlay reacts too: `ControllerImageView.spin_jog(label, delta)` turns a white notch line drawn over each jog/rotary geometry marker (`layout.visual_kind_for(...) == "jog"`), kept as its own `_overlay_jog_notches` item so `spin_jog` can `setLine()` it in place without a full overlay redraw (which would clobber an in-flight `flash_key` mutation). The overlay carries only one `"Jog wheel"` geometry entry (no left/right split), so `_on_live_midi_event` strips the `" (R)"` mirror suffix and spins it whenever this tab shows that controller. `jog.DEGREES_PER_TICK` (`= 6.0`) lives in the Qt-free `gui/jog.py` so both `layout_view` and `controller_image_view` read it without a circular import (`layout_view._JOG_DEGREES_PER_TICK` is a re-export). VU meters (no glyph exists yet — an output-direction feature) still don't react. Polled from a `QTimer` (`MidiMonitor.poll()`), not callback-based, specifically to avoid marshalling rtmidi's background-thread callbacks onto the Qt main thread. `MidiEvent.channel/event_type/data1` are pre-formatted to match `model.Control`'s string convention (1-indexed channel, `"Note On"`/`"Control Change"`, decimal `data1`) so they feed `catalog.lookup()` unchanged. Input-direction monitoring (controller → computer) works on any port; output-direction (Serato → controller) requires the user to manually add this app's self-created virtual destination (`MidiMonitor.VIRTUAL_MONITOR_NAME`) as an *extra* MIDI output in Serato — CoreMIDI does not let a third app silently see what another app sends to a real hardware destination, there is no way around this without that manual step. No physical controller was available while building this: verified end-to-end via macOS's built-in **IAC Driver** virtual ports (already enabled on this machine — `mido.get_input_names()` shows `IAC Driver Bus 1/2`), sending synthetic `mido.Message`s into one and confirming they appear in the log and highlight the correct Layout cell. Requested directly by the user: `LiveMonitorView.ensure_monitoring_started()` opens every port `list_input_ports()` reports and starts the poll timer, called from `MainWindow._load_tree()` right after `set_config()` (and again from `_on_preferences()` if the setting was just turned on with a mapping already loaded) whenever `preferences.auto_start_live_monitor` is true (`PluginPreferences.auto_start_live_monitor`, default `True`, toggled in `PreferencesDialog`) — so `By Channel`/`By Deck`/`By Controller` reflect live controller state as soon as a mapping loads, with no separate "Start monitoring" click. It's a no-op if a session is already running (never overrides ports a user picked by hand on the Live Monitor tab itself), and a port that fails to open is skipped with a logged warning instead of aborting every other port or popping a dialog — unlike the manual "Start monitoring" button, this runs silently in the background.
- **Controller Setup**: `controller_setup.ControllerSetupView` — a self-contained tab (own `MidiMonitor` instance/timer, no wiring into `MainWindow.config` or cross-tab highlighting beyond the one exception below) for building a brand-new `catalog/<slug>.py` module when no official MIDI docs exist yet. It builds a *controller profile* only — never a Serato mapping for editing (that's `File → Open`) — and every help affordance in the tab (a per-group help button plus a persistent hint under the "Draft" panel) says so explicitly, since the tab's own vocabulary ("Import", "trigger", "profile") otherwise reads close enough to mapping-editing terms to invite confusion. Rows (`ControlInfo` itself, reused directly as the table's row type) are populated either by **learning** — pressing buttons while listening, deduped fresh against `(channel, note_or_cc, data1)` on every add via `_maybe_add_row` — or by **importing an existing Serato XML** (`parser.parse_file` → one `_maybe_add_row` call per `<control>`; naturally idempotent against the file's real 10x-duplicated triggers, see below, since XML import and live learning share the same dedup entry point and re-importing adds nothing new). Imported rows only carry the raw trigger — Serato XML has no physical control names — so Section/Name are always typed in by hand. After a successful import, a confirmation dialog offers to also open that same file as an editable Serato mapping (`By Channel` etc.) — the one deliberate exception to "no wiring into `MainWindow.config`": accepting emits `openMappingRequested(path)`, which `MainWindow._on_open_mapping_requested` handles identically to `File → Open` on that path, then switches to `By Channel` so the loaded mapping is immediately visible. Because `_maybe_add_row` only dedups at insertion time, a hand-edited Channel(s)/Type/Data1 cell can still make two rows collide afterwards — a "Check for conflicts" button (and the same check gating "Generate catalog module…") runs `codegen.find_trigger_conflicts`, which flags any raw `(channel, note_or_cc, data1)` trigger claimed by rows with different `(section, name)` as a blocking error (rows that agree on section/name and differ only by channel are fine — that's what `merge_by_channel` folds together, not a conflict). The in-progress draft can be saved/loaded as its own JSON session (`catalog/codegen.py`-independent, `{"version": 1, "controller_name": ..., "reference_image": ..., "rows": [...]}`), distinct from importing a Serato XML. `reference_image` is an optional absolute path to a user-supplied PNG/JPG attached via "Attach reference image…" (issue #16) — never copied into the repo; `build_definition`/`generate_module_source` carry it through (`generate_module_source` writes just the basename, so a bundled copy at `assets/controllers/<basename>` resolves), and `controller_image_view._resolve_image_path` accepts both an absolute path and a bare bundled filename. Both "Apply now (this session)" and export share `codegen.build_definition` (merges via `merge_by_channel`, infers `section_order` via `infer_section_order`) as the single source of truth for what a draft turns into. "Apply now" calls `_registry.register(definition, replace=True)` — `register()` gained a `replace` kwarg (default `False`, unchanged raise-on-duplicate behaviour for every hand-written module's own `register(...)` call) specifically so re-applying an edited draft under the same name updates it instead of erroring. `ControllerSetupView` tracks `self._applied_names: set[str]` (names *this* draft has itself applied) so `_on_apply_clicked` can hard-block (not just confirm) applying under any other already-registered name — the bug this caught in practice: naming a draft "DDJ-XP2" and clicking Apply used to silently replace the real hand-transcribed ~45-entry DDJ-XP2 definition in memory with the tiny draft, breaking every tab that resolves DDJ-XP2 triggers for the rest of the session (recoverable only by restarting the app, since it's in-memory only — the real `ddj_xp2.py` file was never touched). Once applied successfully, emits `controllerApplied(name)`, which `MainWindow._on_controller_applied` uses to call `refresh_controllers()` on `layout_view`/`deck_layout_view`/`controller_layout_view`/`controller_image_view` (new method on `ControllerLayoutView` and `ControllerImageView` — their controller combos were previously populated once at `__init__` and never revisited) and, if a config is loaded, `_refresh_layout_usage()` to rebuild the By Controller tree too. This also required fixing `controller_tree.py`, which had cached `CONTROLLERS = tuple(catalog.CONTROLLER_NAMES)` as a module-level constant at import time instead of reading the registry live inside `build_controller_columns()` as CLAUDE.md already claimed it did — harmless before (all real controllers were registered before this module's own import), but a real bug once mid-session registration was possible. This is all in-memory only — nothing is written to disk and `catalog/__init__.py` is never touched — so it doesn't survive a restart; export (`catalog/codegen.py`'s `generate_module_source`, Qt-free and independently tested) writes the persisted `catalog/<slug>.py` for that, but **never** touches `catalog/__init__.py` either; the one remaining import-line edit documented above stays manual by design (mechanically editing another module's import list was judged a footgun not worth automating). Separately, "Submit to community catalog…" (issue #17, minimal no-backend option) routes the same `build_definition` output through `catalog/community.py` (Qt-free: `build_submission_payload` → versioned `controller-submission/1` dict, `submission_issue_url` → a pre-filled `github.com/<COMMUNITY_REPO>/issues/new?labels=controller-submission&…` link with the JSON inlined in the querystring when it fits under ~6 kB, else a paste placeholder). The GUI handler validates first, always copies the JSON to the clipboard, opens the browser, and never uploads anything itself; `reference_image` is excluded from the payload. The "MIDI input" + "MIDI Output" row (`io_row`) is wrapped in a `QScrollArea` (issue #19): the "MIDI Output" panel's three side-by-side columns (Send message / Playback / Pad modes) need more width than the app's default/minimum window size guarantees, and used to overlap instead of shrinking below their contents' minimum size — verified by screenshotting this tab at 1100x700. The scroll area enforces the row's real minimum size and shows a scrollbar instead. `Available output ports` (`self._output_port_list`) is a checkbox `QListWidget` via `port_list_utils.refresh_checked_port_list`, the same helper `MIDI input`'s port list uses — checking several ports sends/replays/plays-rows to all of them, not just one. `_selected_output_ports()` returns the checked list (raising if empty); every send/play/replay handler loops over it instead of reading a single `currentItem()`. Unlike a fresh `MIDI input` list (nothing pre-checked, since listening indiscriminately would be surprising), `_refresh_output_ports()` auto-checks the first port whenever none are checked — including right after populating a fresh list and after a refresh that finds a deliberately-emptied selection — preserving the old single-output convenience default (sending is only useful with at least one output chosen) while still allowing the user to check more, or fewer, at will.

All editing goes through `edit_panel.py` + `commands.py` (`QUndoStack`-based). Raw nodes (Control/UserIO/MappingElement) edit individually; the "By Deck" columns instead surface `MappingGroup` (`mapping_group.py`) — the set of duplicate Control/MappingElement instances sharing the same trigger and deck/slot/tag/event (i.e. the 10x duplicates) — and edits apply to every member atomically via `SetGroupAttrCommand`/`Add-`/`RemoveGroupAliasCommand`, so it's structurally impossible to edit one duplicate out of sync with its siblings through that view.

Selecting anything in any tab highlights the matching cell(s) (red border) in all three `ControllerLayoutView` instances via `MainWindow._update_layout_selection`, and cross-tab navigation (layout cell click, deck/controller-tree leaf click) always lands on the underlying raw `Control` in the **By Channel** tab, resolved through `MainWindow.node_to_item` + `_channel_model_owner` (maps a source model id to its `(QTreeView, QSortFilterProxyModel)` since each channel is now a separate model/view pair).

`View → Performance Mode` (a checkable `QAction`, session-only like `Show all controllers` — not persisted to `PluginPreferences` or `QSettings`) is an on-stage-friendly toggle for the three tree+layout `QSplitter` pairs (`By Channel`/`By Deck`/`By Controller`): `MainWindow._on_performance_mode_toggled` shrinks each pair's ratio to `_PERFORMANCE_TREE_RATIO` (the tree pane can't fully vanish — `setChildrenCollapsible(False)` — but a ~3% sliver reads as hidden) and calls the new `ControllerLayoutView.set_zoom(_PERFORMANCE_ZOOM_FACTOR)` on all three `ControllerLayoutView` instances (`resetTransform()` + `QGraphicsView.scale()`, mirroring `ControllerImageView`'s existing wheel-zoom). Because `MainWindow.resizeEvent` already re-enforces whatever ratio is recorded in `_pair_ratio_by_id` on every resize, writing the shrunk ratio there (rather than a one-off `_set_pair_ratio` call) makes the tree stay hidden across window resizes for free. Turning it off snapshots+restores the pre-toggle ratios (`_performance_saved_ratios`) and resets zoom to 1.0 exactly, verified by screenshotting the real `MainWindow` offscreen before/on/off and confirming "off" is pixel-identical to "before". Deliberately the smallest of three scoped options (session toggle vs. a persisted `PluginPreferences` field vs. a dedicated fullscreen window) — picked after two research passes scoped the backlog's vague "larger controls and reduced mapping detail" wording into concrete choices.

**Controller Emulator** (`controller_emulator.py`, issue #9, a 5-phase roadmap agreed in-session — see the "Currently modeled" pattern of the geometry chantier for the same one-tagged-milestone-at-a-time discipline; **all 5 phases are now delivered**, per the roadmap's own closing comment on the issue): one or more `Controller Emulator` tool docks, each showing a single controller's interactive, clickable schematic. Clicking a pad/button flashes it and resolves what the *currently loaded* mapping binds that trigger to — dry-run resolution always happens — and, since phase 4, also sends a real MIDI message to a chosen output port when the embedded `LiveSendControl` (`gui/live_send.py`, shared with `ControllerLayoutView`/`ControllerImageView`) is switched on (default off). Since phase 3, dragging a knob/fader/jog glyph vertically sets its value too (`_ClickableEmulatorView`/`_DRAG_KINDS`, reusing `draw_control_glyph()`'s existing knob-rotation/fader-thumb math via `EmulatorLayoutView.set_value()`/`spin_jog()`) — deliberately display-only, not reopening "continuous controls are out of catalog scope" as a side effect: these visual kinds have no `ControlInfo` at all, so a drag only ever moves the glyph, never dry-run-resolves or live-sends (a discrete pad/button click is unaffected, still routed through `controlPressed` as before), and carries no persistent state beyond that one local value. Limited persistent state otherwise (a clicked cell with several raw-trigger variants — SHIFT vs. plain, or one of DDJ-1000's 16 real pad-mode banks — resolves to one fixed default via `layout.pick_default_variant`, **except** that since `v0.47.67` clicking a pad-mode-select button, DDJ-XP2's PAD MODE 1–4 or XDJ-XZ's HOT CUE/BEAT LOOP/SLIP LOOP/BEAT JUMP, records that mode per grid side and steers later pad clicks to its bank — phase 5 slice 2, `gui/pad_mode.py`, a `prefer_token` threaded into `pick_default_variant`; and since `v0.47.68` clicking a **SHIFT** cell latches an instance-wide SHIFT-held state (`_shift_held`, lit while on) that makes an ambiguous cell resolve to its `+SHIFT` variant via a `prefer_shift` flag threaded the same way — a SHIFT geometry marker was added to XDJ-XZ so it's clickable there too, not just DDJ-XP2; and since `v0.47.69` clicking one member of a mutually-exclusive output set — an output mapping carrying a `selected` alias, i.e. every `auto_loop_specific_length` slot on a deck, where `selected`/`off` collide at raw value 0 — records it in `_selected_slot` per `(deck_id, tag)`, lights it, and un-lights the previously-selected sibling: phase 5's last piece, `gui/output_state.is_radio_group`, real per-slot state rather than an on/off flip). Two pieces of reusable plumbing from phase 1, not tied to the emulator: `layout_view.draw_control_glyph()` (extracted verbatim from `ControllerLayoutView._draw_control_shape`, no behavior change — both the read-only By Channel/Deck/Controller schematic and this new interactive one now draw identical glyphs from one place) and `layout.reverse_lookup(controller)` (the inverse of `catalog.lookup()`: every real `ControlInfo` variant collapsing into each layout cell — static entries via direct scan, pad-bank entries via brute-force enumeration of `pad_lookup`'s bounded domain, which works for any bespoke formula, including future community-submitted ones, without hand-inverting it; invalidated in `MainWindow._on_controller_applied` alongside the other `refresh_controllers()` calls). Deliberately does **not** extend `ControllerLayoutView` — that widget's whole contract is a two-controller diff/audit view (tab bar, deck filter, a split-half "what does the *other* controller think this trigger means" row) for the tree tabs, none of which fits a single-controller interactive emulator; `EmulatorLayoutView` is a new sibling widget built from the same free functions instead.

Phase 2 replaced the single fixed dock from phase 1 with **dynamic, multi-instance** emulator windows: `View → New Controller Emulator…` (`MainWindow._create_emulator_instance`) opens another independent instance at any time, each bound to its own controller (e.g. DDJ-XP2 + XDJ-XZ side by side), tracked in `self._emulator_docks: dict[str, QDockWidget]` (an instance id, not the fixed string key `_tool_docks` uses for the always-one Live Monitor/MIDI Routing/MIDI Clock/Metronome docks). Multi-instance was sequenced *before* continuous controls/real MIDI output/stateful simulation (phases 3-5), not after, specifically so those phases are written instance-scoped from the start instead of needing a later retrofit. `_build_emulator_dock_title_bar` mirrors `_build_dock_title_bar`'s Dock/Undock look but wires Close to `_close_emulator_instance` (which actually tears the instance down — `removeDockWidget` + `deleteLater()` — unlike the fixed docks' Close, which just hides a permanent singleton). Which controllers had an emulator open is persisted across restarts (`closeEvent` writes `emulator/open_controllers` to `QSettings`; `_restore_emulator_instances` replays it — as new instances, called from `_restore_user_layout` *before* `restoreState()`, mirroring how the fixed docks already exist before that call). Exact prior geometry/floating state is **not** restored per instance — each dynamically created dock's `objectName` is a fresh random id every session (only needs to be stable *within* a session for Qt to reposition it while docked/floating), so only the *set of open controllers* survives a restart, not their window positions.

Since `v0.47.59` the emulator also reacts to **live** MIDI, passively: `ControllerEmulatorView.flash_live_hit(hit)` briefly flashes the marker a live hit resolves to (via `layout.presentation_key_for_hit(hit)` → `EmulatorLayoutView.flash_key`, the same 220ms pulse a click gives), self-filtered to `hit.controller == current_controller()` so it's a no-op for an instance showing a different controller. `MainWindow._on_live_midi_event` calls it unconditionally over every `_emulator_docks` value, right after the Controller Images overlay flash. Since `v0.47.60` it also holds a persistent amber "held down" highlight from live Note On/Off: `ControllerEmulatorView.set_live_active_from_hit(hit, active)` → `EmulatorLayoutView.set_live_active`, which keeps a `_live_active_keys` set **separate from** the phase-5 click-toggle `_active_keys` (so a live press and a click-toggle don't stomp each other) but OR's them everywhere the render reads `_active_keys`. The emulator's dry-run *resolution* stays click-only. Since `v0.47.61` it also shows *latched* LED state from output-direction MIDI: `ControllerEmulatorView.set_led_from_hit(hit, on)` → `EmulatorLayoutView.set_led`, a third `_led_keys` set OR'd into the amber render alongside `_active_keys`/`_live_active_keys` but never cleared by an input-direction release (see the Live Monitor bullet's output-direction slice).

`Help` menu links to the source docs (Serato's MIDI mapping guide is Cloudflare-protected and can't be fetched programmatically — `WebFetch`/`curl` both get a bot-challenge page, not the article).

### `library/` — music-library scan and index (foundation)

A new, separate domain from everything else in this project: rather than editing MIDI *mappings*, this manages the DJ's actual music collection (tagging, genre normalization, BPM/key, and Serato/Traktor/rekordbox playlist tooling) — scoped in GitHub milestone "Music library management" (#5) and tracking issue #133, after the maintainer's own real collection (674 GB, 85,607 audio files) proved too disorganized to build mixable playlists from by hand.

`library/db.py`'s `LibraryDB` is the local SQLite source of truth for the scanned index (one `roots` row per configured music folder, one `tracks` row per indexed file recording only `path`/`size`/`mtime`/`missing` — never file content or tags) and `library/scanner.py`'s `scan_root()` walks a root incrementally: a file whose size/mtime haven't changed since the last scan is skipped rather than re-touched, and a file that disappears is flagged `missing` rather than deleted from the index, so a temporarily-unmounted drive or a rename doesn't lose history. `iter_audio_files()` filters to `AUDIO_EXTENSIONS` (mp3/wav/aiff/flac/m4a/ogg/aac) and skips macOS AppleDouble sidecars (`._*`) and hidden directories (`.Trash`, `.fseventsd`, …), both found throughout the maintainer's real collection. Deliberately Qt-free, like `model.py`/`parser.py` — a future GUI tab (issue #132, sequenced last) wraps scanning in whatever non-blocking mechanism it needs (this project's `QTimer`-polled MIDI monitoring is the established precedent, not a blocking loop) rather than this module depending on Qt itself.

The scan/index itself is strictly read-only against the real collection (issue #125) — no code in `db.py`/`scanner.py` writes to an audio file, a tag, or any DJ software's own library/playlist files. `metadata.py` (below, issue #126) is the first piece that writes, deliberately scoped to real per-file tags only, never the scan index's own bookkeeping. Later sub-issues (#127 genre taxonomy, #128 BPM/key analysis, #129/#130/#134 Serato/Traktor/rekordbox library formats, #131 playlist generation, #132 the GUI tab) build on this index; see #133 for the full breakdown, feasibility notes, and sequencing, including real-fixture findings from investigating the maintainer's own `_Serato_`/`_Traktor`/`PIONEER/rekordbox` folders.

### `library/metadata.py` — non-destructive audio metadata read/write (issue #126)

A `mutagen` wrapper (added as a real dependency via `uv add mutagen`) exposing a normalized `TrackMetadata` dataclass (`title`/`artist`/`album`/`genre`/`bpm`/`key`/`comment`/`rating`/`energy`) through `read_metadata(path) -> TrackMetadata | None` (`None` only for a file mutagen can't parse at all — an untagged-but-valid audio file reads back as all-`None` fields) and `write_metadata(path, **fields)`, working across MP3/AIFF (ID3 frames, both share `mutagen`'s `ID3`-subclass tag object), FLAC/OGG (Vorbis comments — `mutagen.flac.FLAC`/`mutagen.oggvorbis.OggVorbis` share the identical dict-like `VCommentDict` interface, so both formats reuse the same `_read_vorbis`/`_write_vorbis` helpers), and M4A (MP4 atoms, including freeform `----:com.apple.iTunes:*` atoms for `key`/`rating`/`energy`, which have no standard atom).

`MANAGED_FIELDS` (mirrors `TrackMetadata`'s own field names, checked by a test) is the explicit allowlist of what this app ever touches; `write_metadata` raises on any other keyword. Every write is frame-level and surgical by construction — `_write_id3`/`_write_vorbis`/`_write_mp4` only ever call `setall`/`__setitem__`/`__setitem__` on the one frame ID or key a field maps to (e.g. `title` → ID3 `TIT2` / Vorbis `title` / MP4 `\xa9nam`), never a full-tag clear-and-rebuild, so this is the single correctness property the tests are built around: `test_write_mp3_preserves_serato_and_traktor_frames_byte_identical` and `test_write_flac_preserves_serato_vorbis_comments_byte_identical` each build a synthetic file carrying fake Serato `GEOB`/`serato_*` blobs and a fake `PRIV:TRAKTOR4` blob, perform an unrelated managed-field write, and assert those frames'/keys' raw bytes are unchanged. The primary ID3 comment is the `COMM` frame with an empty `desc` (`COMM::eng` in mutagen's own key notation) — distinguished from every other `COMM` frame a real file may carry (an ID3v1 mirror, old-software preference frames), which `write_metadata` always leaves untouched by re-adding them verbatim alongside whatever it changes.

`clean_noise_frames(path, dry_run=True) -> list[str]` reports (and, only on an explicit `dry_run=False` call, removes) the real noise patterns confirmed against the maintainer's own files in issue #126's investigation comment: duplicate ID3v1 `COMM` mirrors (`desc="ID3v1 Comment"`), `COMM:Songs-DB_Preference`/`COMM:MusicMatch_Preference`, `PRIV` frames with a `WM/`-prefixed owner, and `replaygain_*`/`LABELNO` (ID3 `TXXX` description or Vorbis comment key, case-insensitive — both ecosystems use the same names). It never touches a `GEOB` frame whose `desc` starts with `"Serato "`, a `PRIV:TRAKTOR4` frame, a Vorbis comment key starting with `serato_`, or `TXXX:EnergyLevel`/`TXXX:STYLE` (real signal the issue explicitly called out to preserve) — checked defensively (protection is checked before any noise pattern can match) rather than relying on the noise patterns simply not overlapping.

Deliberately out of scope for #126: decoding Serato's own proprietary Autotags binary blob to read its embedded BPM/key. That format isn't documented anywhere this project could verify against (the same "never fabricate binary structure without official docs" discipline `catalog/` already applies to controller MIDI data), so `read_metadata` reads the standard `TBPM`/`TKEY` (ID3), `bpm`/`key`/`initialkey` (Vorbis), and `tmpo`/freeform `initialkey` (MP4) tags instead — left for the BPM/key analysis sub-issue (#128) to revisit if a documented way to read Serato's own analysis ever surfaces. `AIFF` support comes for free from the ID3 code path (`mutagen.aiff.AIFF.tags` is an `ID3` subclass) despite not being one of the three formats explicitly exercised by name in tests. OGG's Vorbis-comment code path is exercised by its own roundtrip tests using a hand-built minimal Ogg bitstream (identification + comment header packets via `mutagen.ogg.OggPage`), separate from — but running the exact same `_read_vorbis`/`_write_vorbis` functions as — FLAC's.

#### `rekordbox_library.py` — Rekordbox `export.pdb` (issue #134)

Reads a Rekordbox USB/device export's `export.pdb` (the maintainer's real fixture: `/Users/guillain/Music/PIONEER/rekordbox/export.pdb`, 3.8 MB) — a completely different file/format from `software/rekordbox/README.md`'s Rekordbox MIDI *controller-mapping* CSV research (that's remapping hardware buttons; this is the track/playlist library), hence the distinct module name. `parse_export(pdb_path) -> list[RekordboxTrack]` resolves each track's artist/album/genre/label/key names via the file's own lookup tables rather than exposing raw internal row IDs; `parse_playlists(pdb_path) -> list[RekordboxPlaylist]` returns the playlist/folder tree (`parent_id`/`is_folder`) with each playlist's `track_ids` in real, `entry_index`-sorted order.

**Dependency decision**: `pyrekordbox` (PyPI, MIT, installs cleanly under this project's Python 3.14) is this project's preferred, actively-maintained dependency for Rekordbox — but only for the formats it actually supports. Inspecting its installed source (v0.4.4) confirmed it covers `master.db` (encrypted SQLite, explicitly out of scope per issue #134), `RekordboxXml`, ANLZ analysis files, and My-Settings files — never this legacy `export.pdb` table format; its own README recommends `rekordcrate`/`crate-digger` (Rust/Java) for "device exports" instead, and an unreleased `devicelib_plus` module on its master branch targets a different, newer, also-encrypted per-device format (`exportLibrary.db`), not this one. The one PyPI-named candidate that turned up in search results, `rekordbox-pdb`, does not actually exist on PyPI (404) — only as a two-star, single-commit GitHub repo, too thin a provenance to depend on for real personal library data. So `rekordbox_library.py` is a from-scratch, dependency-free binary parser instead, hand-written directly against Deep Symmetry crate-digger's published `rekordbox_pdb.ksy` Kaitai Struct spec (a factual byte-layout reference the same way a controller's official MIDI Message List PDF is for `catalog/`, not code copied from it) and verified byte-for-byte against the maintainer's real `export.pdb` during development (6,513 tracks; 27 playlists/folders with correct parent/child nesting; titles, artists, albums, genres, labels, musical keys, BPM, comments, and file paths all read correctly) — read-only, nothing under `/Users/guillain/Music` was ever written by this work.

**Test coverage honesty**: `tests/test_rekordbox_library.py` is a genuine end-to-end test, not just wrapper-logic unit tests — it hand-builds a minimal synthetic `export.pdb` (real page header, row-index bitmask/offset backward-indexing, and DeviceSQL string encoding, all independently re-derived in the test file rather than importing the module's own constants) and parses it through the real `parse_export`/`parse_playlists` entry points, alongside direct tests of the DeviceSQL string codec (`decode_device_sql_string`) against all three encodings (short ASCII, long ASCII, long UTF-16LE). The real file was used only for manual, interactive verification during development (see above) and is never read by the committed test suite.

**Scope cut**: `exportExt.pdb` (the "My Tag" sidecar table format) is not implemented — out of scope per issue #134's own conservative-scoping instruction, and genuinely a different row-type set (`tag_row`/`tag_track_row`) the Kaitai spec calls out separately. Track color, cue points, and artwork paths are also not exposed on `RekordboxTrack` (straightforward to add later following the same offset-table pattern, just not included in this first pass).

### `library/traktor_library.py` — Traktor `collection.nml` read support (issue #130)

A completely different Traktor file from `software/traktor/README.md`'s `.tsi` *MIDI controller mapping* format — this one is Traktor's *track collection* (tracks + playlists), confirmed against the maintainer's real `/Users/guillain/Music/_Traktor/collection.nml` (Traktor Pro 4, `NML VERSION="20"`, 44,564 `<COLLECTION><ENTRY>` elements) read-only (never written to, per this initiative's standing rule).

Confirmed real shape: each `<ENTRY TITLE="..." ARTIST="...">` holds a `<LOCATION DIR="..." FILE="..." VOLUME="..."/>` (Traktor's own path encoding — `DIR`/`FILE` use `"/:"` as the path-component separator, a holdover from classic Mac OS `:`-separated paths), an `<INFO KEY="7m" .../>` (a human-readable Camelot/Open-Key-style string), a `<TEMPO BPM="..." .../>`, and a `<MUSICAL_KEY VALUE="15"/>` (Traktor's internal numeric key code, independent of `INFO`'s display string). After `</COLLECTION>` there is a top-level `<PLAYLISTS>` section: a `<NODE TYPE="FOLDER" NAME="$ROOT">` containing `<SUBNODES>` of either `<NODE TYPE="SMARTLIST">` (a saved search query, e.g. `$RATING == 5` — no explicit track list) or `<NODE TYPE="PLAYLIST">` wrapping a `<PLAYLIST ENTRIES="N">` of `<ENTRY><PRIMARYKEY TYPE="TRACK" KEY="..."/></ENTRY>` — that `KEY` is exactly `VOLUME + DIR + FILE` concatenated verbatim, which is how a playlist entry joins back to a collection track (verified byte-for-byte against the real file).

`parse_collection(path)` streams the file with `xml.etree.ElementTree.iterparse` (`events=("end",)`), calling `.clear()` on each `<ENTRY>` right after building its `NmlTrack` — this is necessary, not cosmetic, at 44,564 real entries: verified end-to-end against the real file (~0.5s, ~61MB peak RSS, vs. a full `ET.parse`/`fromstring` load of the whole tree). `NmlTrack` carries `title`/`artist`/`location`/`key`/`bpm`/`musical_key` (the `INFO` display string)/`musical_key_value` (the numeric code)/`album`/`volume`; `location` is `DIR+FILE` with `"/:"` swapped for `"/"` but **without** the volume prefixed — this project has no reliable way to know how a given `VOLUME` is actually mounted (the maintainer's real file only ever uses one, `"Macintosh HD"`, the boot volume, which mounts at `/` rather than a guessable `/Volumes/<name>`), so guessing was avoided; `key` keeps the raw, unambiguous `VOLUME+DIR+FILE` string instead, since that's what actually joins to a playlist entry.

`parse_playlists(path)` also uses `iterparse`, `.clear()`-ing every `COLLECTION/ENTRY` it passes over the same way (so this function is equally memory-bounded on the real file despite `<PLAYLISTS>` sitting after the large `<COLLECTION>` section) and then, once the small `<PLAYLISTS>` element itself closes, walking its already-fully-built subtree with `.iter("NODE")` to collect every `TYPE="PLAYLIST"` node's name → ordered list of `PRIMARYKEY` `KEY` strings (a plain `.iter()` walk handles folder nesting at any depth for free, though the maintainer's real file only nests one level deep) — `TYPE="SMARTLIST"` nodes are skipped since they carry no track list to read. Verified against the real file's `<PLAYLISTS>` section (6 real playlists, e.g. `"Spotifion"` with 192 entries; 3 smartlists correctly excluded).

Writing a `.nml`-compatible playlist back out was scoped as a nice-to-have and deliberately **not implemented this pass** — reading was the stated priority and this delivers it fully; a future pass can add export following the same "only ever write to a caller-specified new path, never touch a real file" discipline as the rest of this initiative. `tests/test_traktor_library.py` uses a small, hand-written synthetic fixture (3 entries, 1 real playlist, 1 smartlist) matching this confirmed shape — never a copy of the real file, which is 51.7MB of the maintainer's personal library data and stays out of the repo entirely.

## What this project is

DJ MIDI Studio: a tool to simplify managing, visualizing, and modifying Serato DJ Pro MIDI configuration files (XML), which can run to 16,000+ lines. Planned capabilities (see README.md):

- **XML Parsing & Modeling**: parse Serato MIDI config XML into a structured object-oriented model (Decks, Channels, Notes, Slots, etc.)
- **Visual Mapping Editor**: GUI to visualize/modify MIDI mappings — object attributes (on/off values, colors) and associated events (Click, Output)
- **Validation**: catch mapping conflicts or invalid XML structure after edits
- **Export**: write a clean, valid XML file re-importable into Serato DJ Pro

## Domain model (Serato MIDI XML format)

`data/xdj_xz-ddj_xp2-4decks.xml` is the user's real, current Serato config (XDJ-XZ/DDJ-XP2, 4 decks) and the best reference for the XML shape — also used as the primary test fixture:

- Root `<midi app="...">` contains a flat list of `<control channel="..." event_type="..." control="...">` elements — these are the raw MIDI trigger (channel/note/control number).
- Each `<control>` holds `<userio event="click">` and/or `<userio event="output">` blocks.
- Inside a `userio` block, one or more mapping elements (tag name = the Serato function, e.g. `codfather_st`, `auto_loop_roll_specific_length`) carry `deck_set`, `deck_id`, `slot_id` attributes.
- Each mapping element contains a `<translation action_on="press|any|..." behaviour="toggle|explicit|...">`, optionally with `<alias name="on|off|selected" value="...">` children mapping logical states to raw MIDI values.

Any XML parsing/modeling code should be validated against this sample file's structure.

This project uses `uv` (build backend is `uv_build`, Python `>=3.14`).
