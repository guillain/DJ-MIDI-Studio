# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

All phases of the original plan are implemented and tested against the user's real config file: `model.py` (domain dataclasses), `parser.py` (XML → model), `exporter.py` (model → XML, byte-for-byte round-trip on the sample file), `validator.py` (structural + conflict checks), `catalog/` (channel/NOTE-CC/data1 → physical control name, see below — the user's real setup mixes DDJ-XP2 and XDJ-XZ in one config, so lookups always check every registered controller and can return ambiguous matches), `gui/` (PySide6 UI, see below). Root `main.py` is unrelated leftover PyCharm boilerplate, not part of the package. `library/` (see below) is a newer, separate initiative for managing the DJ's actual music collection rather than MIDI mappings.

### `catalog/` — plugin-style controller registry

`catalog.py` was split into a package: `catalog/_registry.py` (the `ControllerDefinition`/`ControlInfo` dataclasses and a plain-dict registry), one module per controller (`ddj_xp2.py`, `xdj_xz.py`), and `catalog/__init__.py` (imports each controller module for its registration side effect, re-exports the public API). Scope per controller is intentionally limited to discrete press/toggle controls (buttons, pad grids) — continuous controls (faders, TRIM/EQ knobs, jog wheels, touch strips/encoders) are left out since they're rarely remapped in Serato configs and don't reduce to one readable name.

**To add a new controller with official docs in hand**: write one new `catalog/<name>.py` module (static entries + a pad-grid function — use `_registry.make_sequential_pad_lookup(...)` if the note layout is simply `(pad-1) + mode_index*16`, otherwise write a bespoke one like `ddj_xp2.py`'s), end it with `register(ControllerDefinition(...))`, and import that module from `catalog/__init__.py`. Nothing else needs to change: `catalog.CONTROLLER_NAMES`/`PAD_COUNTS` are computed live from the registry on every access (module-level `__getattr__`, not a snapshot — a controller registered after the package is imported, e.g. interactively, is picked up immediately), and the Layout/By-Controller/Controller-Images tabs' combos all read from `CONTROLLER_NAMES` rather than a hardcoded list. Full docstring/steps in `catalog/__init__.py`; `tests/test_catalog_registry.py` exercises this end-to-end by registering a throwaway controller and checking it shows up in `lookup()` and `gui.layout.build_layout()`. See `~/.claude/plans/sprightly-questing-bengio.md` for the original phased plan (predates this package split).

**To add a controller with no official docs** (the original blocker for the user's Behringer CMD LC-1 — since done, `catalog/behringer_cmd_lc_1.py`, captured on the real unit: 52 static NOTE entries on channel 8, encoders out of scope; macOS names its port `CMD LC-1`, so it sets the new optional `ControllerDefinition.port_names` that `detect_controller` matches with the same score-100 weight as `name` — and a "miniPad"): use the GUI's **Controller Setup** tab (see below) instead of transcribing a PDF by hand — it generates a `catalog/<slug>.py` module ready for the one manual import-line step above, either from live-learned MIDI or from an existing Serato XML's triggers.

### Empirical finding: the 10x duplication

In the user's real file, every unique `(channel, event_type, control)` trigger is repeated verbatim 10 times (64 unique triggers × 10 = 640 total `<control>` elements — confirmed via `build_mapping_groups`/`_check_duplicate_triggers`). This is **not** export bloat: the user confirmed deleting the "duplicates" breaks the config in Serato. The reason for exactly 10 is still unconfirmed (best guess: some internal Serato state not represented in this XML format, e.g. auto-loop length presets), but treat it as load-bearing. `validator.py` flags identical-content duplicates as `info`, explicitly saying not to deduplicate — never change that to `error`/cleanup advice without new evidence.

### GUI structure (`gui/`)

`left_tabs` has six tabs. The first three pair a tree (one resizable column per channel/deck/controller — implemented via `QSplitter(Horizontal)`, not a single nested tree) with a `layout_view.py` `ControllerLayoutView` DJ-oriented layout of the same underlying data. The renderer uses compact pad, button, knob, fader, and jog glyphs inferred from catalog vocabulary, with a generic fallback for unknown controls. For a controller with `gui/geometry.CONTROL_GEOMETRY`, the layout switches to real-position mode (markers at each control's true photographed coordinate; see the module docstring / TODO.md's DJ-layout-visual-fidelity chantier), and the **`Controller` display layer** (on by default; a `"Controller photo"` checkbox before `v0.48.45`) then draws the real reference photo behind those markers via `layout_view.draw_reference_photo()` — `ControllerEmulatorView` carries the same checkbox for `EmulatorLayoutView`, also on by default. No effect in the classic card-grid fallback (a controller with no geometry). Not persisted — the default reapplies each session.
- **By Channel**: `tree_model.build_channel_columns()` (one column per MIDI channel, each Note/Control → Control → UserIO → Mapping) + a plain `ControllerLayoutView` colored by which Serato deck(s) use each control.
- **By Deck**: `deck_tree.build_deck_columns()` (one column per Serato deck, each Slot → function) + `ControllerLayoutView(show_deck_filter=True)`, whose combo narrows the coloring to one selected deck.
- **By Controller**: `controller_tree.build_controller_columns()` (one column per controller — DDJ-XP2, XDJ-XZ — grouped by catalog section; sections with no used entries stay collapsed) + a third plain `ControllerLayoutView`. A leaf here can represent dozens of real `<control>` elements at once (a whole pad-mode grid cell), so clicking one reuses `MainWindow._on_layout_cell_activated` rather than feeding the edit panel directly.
- **Controller Images**: `controller_image_view.ControllerImageView` — a static, zoomable/pannable viewer (no data binding) for the official Pioneer controller diagrams in `controllers/<slug>/*.png` (one common directory; since the controllers-by-vendor reorg, real devices live under `controllers/hardware/<vendor>/<Model>/` — e.g. `hardware/pioneer/DDJ-XP2/`, `hardware/behringer/CMD-micro/` — and every `reference_image`/document path is relative to `controllers/` in that form; one subdirectory per controller holding everything for it — artwork and source PDF together, see `controllers/README.md`; a `controllers/custom/` subdirectory is reserved for Controller Setup exports — committed to the repo for personal/reference use only — the Pioneer/AlphaTheta ones are copyrighted images, not to be assumed clear for redistribution beyond that; as of `v0.47.95-controller-assets-reorg` this replaced the previous, split `assets/controllers/`/`docs/controllers/` layout, see that TODO.md entry — CLAUDE.md's and TODO.md's own older narrative below still describes files by their pre-reorg `assets/controllers/<slug>.png` paths, left as an accurate historical record rather than rewritten). Each controller bundles **two variants** under a `reference.png` (clean device render) / `reference-midi.png` (the same view with the MIDI Message List's callouts printed over it) naming convention, both inside that controller's own `controllers/<slug>/` directory — `controller_image_view.image_variants(reference_image)` resolves the pair from either name — and a **"MIDI info" checkbox** swaps between them (disabled when a controller only ships one variant, e.g. a Controller Setup attachment). The checkbox defaults to whichever variant that controller's `catalog` `reference_image` actually names, and once the user toggles it their choice is pinned across controller switches (`self._midi_override`). - **Live Monitor**: `live_monitor.LiveMonitorView`, backed by `midi_io.py`. Watches real MIDI traffic and drives the same three `ControllerLayoutView`s (plus the Controller Images overlay and every open Controller Emulator dock) via `MainWindow._on_live_midi_event`, which does five independent things (issue #13 part 2): `_update_layout_selection` sets the persistent (until the next selection) red selection border; `flash_key(key)` briefly (220ms, `QTimer.singleShot`) turns a discrete pad/button glyph white to mimic it lighting up on a real hit; `set_value(key, event.data2)` records the live 7-bit value for a knob/fader glyph, rotating a knob's marker (-135 to +135 degrees, a typical pot sweep) or moving a fader's thumb within its track — a level, not a pulse, so it persists like a real control staying wherever it was left; and (since `v0.47.60`) `set_active(key, bool)` holds a steady **amber "held down" highlight** (`_ACTIVE_BORDER_PEN` border + translucent amber fill, the emulator's phase-5 toggle look) — lit on a live Note On (`data2 > 0`), cleared on Note Off / velocity-0. A release resolves against `"Note On"` too (catalog entries are all stored that way) so the selection/highlight tracks the just-released control instead of vanishing; a plain CC leaves held state alone; and set_active runs *before* flash_key so the 220ms white pulse always paints on top of the amber. Because a red selection border and the amber active border can't both show, selection wins the border and the amber *fill* keeps "held" visible underneath. That `set_active` path is the **input-direction** slice (Note On/Off = press/release). Since `v0.47.61` there is also an **output-direction** slice: `MidiEvent.direction == "out"` events (Serato → controller LED feedback, seen on the virtual monitor port `MidiMonitor.VIRTUAL_MONITOR_NAME`) are routed to `_on_output_led_event` *before* any of the above and drive `set_led(key/label, on)` on the same three `ControllerLayoutView`s, the Controller Images overlay, and every open emulator dock (`ControllerEmulatorView.set_led_from_hit`). The LED highlight is **latched** — lit on a Note On with velocity > 0, cleared on Note Off / velocity 0 — reuses the identical amber `_ACTIVE_BORDER_PEN` look, and lives in a `_led_keys`/`_led_labels` set **kept separate** from the input-direction `_active_keys` so an input-direction release can't clear an LED the software is still driving (rendered as `key in _active_keys or key in _led_keys`). Output-direction events do **not** flash, change the selection, or touch `set_value`; a CC on the output port is ignored (no LED meaning). The LED note number is **assumed equal to the input trigger note** — Serato's own convention for nearly every mapping, and there's no per-control `led_note` field in the catalog — so a controller that lights a different note than it sends won't resolve. **Jog-wheel rotation** does react, since `v0.47.62`: a jog turn is a stream of relative Control Change ticks that deliberately have *no* catalog entry (continuous controls are out of catalog scope), so `_on_live_midi_event` resolves it against `gui/jog.py`'s small per-controller table instead — **XDJ-XZ** (platter CC `0x22`/`0x29`, wheel-side CC `0x21`/`0x26`; decks 1/3 → left "Jog wheel", 2/4 → right-tray "Jog wheel (R)") and, **DDJ-1000** (`v0.47.64`, platter CC `0x21`/`0x29`/`0x1F`), **DDJ-FLX10** (`v0.47.65`, platter CC `0x22`/`0x23`/`0x29`/`0x1F` + wheel-side `0x21`/`0x26`) and **DDJ-REV1** (`v0.47.66`, same as FLX10 minus `0x29`) — all 2-deck, all schematics draw only the left deck so every deck channel resolves to their one "Jog wheel". All on the deck channel with the same `0x40`-centred relative encoding read from each controller's MIDI Message List rendered table. Many of these CCs collide (e.g. `0x21` is used by all four on the deck channel), so `jog_cell_keys_for_event` returns *every* matching marker and each view spins only the controller it shows. Single-jog controllers are a `(data1 set, key)` table in `gui/jog.py`; XDJ-XZ is the one special case, resolved side-aware by deck channel. `_on_live_midi_event` decodes the signed delta (`decode_jog_delta`), and integrates it into each jog glyph's notch angle via `ControllerLayoutView.spin_jog` / `EmulatorLayoutView.spin_jog` (a running 0–360° accumulator in `_jog_angles`, `_JOG_DEGREES_PER_TICK = 6.0` — a cosmetic gain, not the platter's real ~1440-tick/rev resolution). The jog branch runs *before* `_update_layout_selection` and early-returns, so a jog turn never flashes, moves the red selection, or touches `set_value`; deck 1/3 → the left "Jog wheel" cell, deck 2/4 → the right-tray "Jog wheel (R)" cell (same split as the pad grids). Since `v0.47.63` the Controller Images overlay reacts too: `ControllerImageView.spin_jog(label, delta)` turns a white notch line drawn over each jog/rotary geometry marker (`layout.visual_kind_for(...) == "jog"`), kept as its own `_overlay_jog_notches` item so `spin_jog` can `setLine()` it in place without a full overlay redraw (which would clobber an in-flight `flash_key` mutation). Phase 2 replaced the single fixed dock from phase 1 with **dynamic, multi-instance** emulator windows: `View → New Controller Emulator…` (`MainWindow._create_emulator_instance`) opens another independent instance at any time, each bound to its own controller (e.g. DDJ-XP2 + XDJ-XZ side by side), tracked in `self._emulator_docks: dict[str, QDockWidget]` (an instance id, not the fixed string key `_tool_docks` uses for the always-one Live Monitor/MIDI Routing/MIDI Clock/Metronome docks). ### `library/` — music-library scan and index (foundation)

A new, separate domain from everything else in this project: rather than editing MIDI *mappings*, this manages the DJ's actual music collection (tagging, genre normalization, BPM/key, and Serato/Traktor/rekordbox playlist tooling) — scoped in GitHub milestone "Music library management" (#5) and tracking issue #133, after the maintainer's own real collection (674 GB, 85,607 audio files) proved too disorganized to build mixable playlists from by hand.

`library/db.py`'s `LibraryDB` is the local SQLite source of truth for the scanned index (one `roots` row per configured music folder, one `tracks` row per indexed file recording only `path`/`size`/`mtime`/`missing` — never file content or tags) and `library/scanner.py`'s `scan_root()` walks a root incrementally: a file whose size/mtime haven't changed since the last scan is skipped rather than re-touched, and a file that disappears is flagged `missing` rather than deleted from the index, so a temporarily-unmounted drive or a rename doesn't lose history. `iter_audio_files()` filters to `AUDIO_EXTENSIONS` (mp3/wav/aiff/flac/m4a/ogg/aac) and skips macOS AppleDouble sidecars (`._*`) and hidden directories (`.Trash`, `.fseventsd`, …), both found throughout the maintainer's real collection. Deliberately Qt-free, like `model.py`/`parser.py` — a future GUI tab (issue #132, sequenced last) wraps scanning in whatever non-blocking mechanism it needs (this project's `QTimer`-polled MIDI monitoring is the established precedent, not a blocking loop) rather than this module depending on Qt itself.

The scan/index itself is strictly read-only against the real collection (issue #125) — no code in `db.py`/`scanner.py` writes to an audio file, a tag, or any DJ software's own library/playlist files. `metadata.py` (below, issue #126) is the first piece that writes, deliberately scoped to real per-file tags only, never the scan index's own bookkeeping. Later sub-issues (#127 genre taxonomy, #128 BPM/key analysis, #129/#130/#134 Serato/Traktor/rekordbox library formats, #131 playlist generation, #132 the GUI tab) build on this index; see #133 for the full breakdown, feasibility notes, and sequencing, including real-fixture findings from investigating the maintainer's own `_Serato_`/`_Traktor`/`PIONEER/rekordbox` folders.

### `library/metadata.py` — non-destructive audio metadata read/write (issue #126)

A `mutagen` wrapper (added as a real dependency via `uv add mutagen`) exposing a normalized `TrackMetadata` dataclass (`title`/`artist`/`album`/`genre`/`bpm`/`key`/`comment`/`rating`/`energy`) through `read_metadata(path) -> TrackMetadata | None` (`None` only for a file mutagen can't parse at all — an untagged-but-valid audio file reads back as all-`None` fields) and `write_metadata(path, **fields)`, working across MP3/AIFF (ID3 frames, both share `mutagen`'s `ID3`-subclass tag object), FLAC/OGG (Vorbis comments — `mutagen.flac.FLAC`/`mutagen.oggvorbis.OggVorbis` share the identical dict-like `VCommentDict` interface, so both formats reuse the same `_read_vorbis`/`_write_vorbis` helpers), and M4A (MP4 atoms, including freeform `----:com.apple.iTunes:*` atoms for `key`/`rating`/`energy`, which have no standard atom).

`MANAGED_FIELDS` (mirrors `TrackMetadata`'s own field names, checked by a test) is the explicit allowlist of what this app ever touches; `write_metadata` raises on any other keyword. Every write is frame-level and surgical by construction — `_write_id3`/`_write_vorbis`/`_write_mp4` only ever call `setall`/`__setitem__`/`__setitem__` on the one frame ID or key a field maps to (e.g. `title` → ID3 `TIT2` / Vorbis `title` / MP4 `\xa9nam`), never a full-tag clear-and-rebuild, so this is the single correctness property the tests are built around: `test_write_mp3_preserves_serato_and_traktor_frames_byte_identical` and `test_write_flac_preserves_serato_vorbis_comments_byte_identical` each build a synthetic file carrying fake Serato `GEOB`/`serato_*` blobs and a fake `PRIV:TRAKTOR4` blob, perform an unrelated managed-field write, and assert those frames'/keys' raw bytes are unchanged. The primary ID3 comment is the `COMM` frame with an empty `desc` (`COMM::eng` in mutagen's own key notation) — distinguished from every other `COMM` frame a real file may carry (an ID3v1 mirror, old-software preference frames), which `write_metadata` always leaves untouched by re-adding them verbatim alongside whatever it changes.

`clean_noise_frames(path, dry_run=True) -> list[str]` reports (and, only on an explicit `dry_run=False` call, removes) the real noise patterns confirmed against the maintainer's own files in issue #126's investigation comment: duplicate ID3v1 `COMM` mirrors (`desc="ID3v1 Comment"`), `COMM:Songs-DB_Preference`/`COMM:MusicMatch_Preference`, `PRIV` frames with a `WM/`-prefixed owner, and `replaygain_*`/`LABELNO` (ID3 `TXXX` description or Vorbis comment key, case-insensitive — both ecosystems use the same names). It never touches a `GEOB` frame whose `desc` starts with `"Serato "`, a `PRIV:TRAKTOR4` frame, a Vorbis comment key starting with `serato_`, or `TXXX:EnergyLevel`/`TXXX:STYLE` (real signal the issue explicitly called out to preserve) — checked defensively (protection is checked before any noise pattern can match) rather than relying on the noise patterns simply not overlapping.

Deliberately out of scope for #126: decoding Serato's own proprietary Autotags binary blob to read its embedded BPM/key. #### `rekordbox_library.py` — Rekordbox `export.pdb` (issue #134)

Reads a Rekordbox USB/device export's `export.pdb` (the maintainer's real fixture: `/Users/guillain/Music/PIONEER/rekordbox/export.pdb`, 3.8 MB) — a completely different file/format from `software/rekordbox/README.md`'s Rekordbox MIDI *controller-mapping* CSV research (that's remapping hardware buttons; this is the track/playlist library), hence the distinct module name. `parse_export(pdb_path) -> list[RekordboxTrack]` resolves each track's artist/album/genre/label/key names via the file's own lookup tables rather than exposing raw internal row IDs; `parse_playlists(pdb_path) -> list[RekordboxPlaylist]` returns the playlist/folder tree (`parent_id`/`is_folder`) with each playlist's `track_ids` in real, `entry_index`-sorted order.

**Dependency decision**: `pyrekordbox` (PyPI, MIT, installs cleanly under this project's Python 3.14) is this project's preferred, actively-maintained dependency for Rekordbox — but only for the formats it actually supports. Inspecting its installed source (v0.4.4) confirmed it covers `master.db` (encrypted SQLite, explicitly out of scope per issue #134), `RekordboxXml`, ANLZ analysis files, and My-Settings files — never this legacy `export.pdb` table format; its own README recommends `rekordcrate`/`crate-digger` (Rust/Java) for "device exports" instead, and an unreleased `devicelib_plus` module on its master branch targets a different, newer, also-encrypted per-device format (`exportLibrary.db`), not this one. The one PyPI-named candidate that turned up in search results, `rekordbox-pdb`, does not actually exist on PyPI (404) — only as a two-star, single-commit GitHub repo, too thin a provenance to depend on for real personal library data. So `rekordbox_library.py` is a from-scratch, dependency-free binary parser instead, hand-written directly against Deep Symmetry crate-digger's published `rekordbox_pdb.ksy` Kaitai Struct spec (a factual byte-layout reference the same way a controller's official MIDI Message List PDF is for `catalog/`, not code copied from it) and verified byte-for-byte against the maintainer's real `export.pdb` during development (6,513 tracks; 27 playlists/folders with correct parent/child nesting; titles, artists, albums, genres, labels, musical keys, BPM, comments, and file paths all read correctly) — read-only, nothing under `/Users/guillain/Music` was ever written by this work.

**Test coverage honesty**: `tests/test_rekordbox_library.py` is a genuine end-to-end test, not just wrapper-logic unit tests — it hand-builds a minimal synthetic `export.pdb` (real page header, row-index bitmask/offset backward-indexing, and DeviceSQL string encoding, all independently re-derived in the test file rather than importing the module's own constants) and parses it through the real `parse_export`/`parse_playlists` entry points, alongside direct tests of the DeviceSQL string codec (`decode_device_sql_string`) against all three encodings (short ASCII, long ASCII, long UTF-16LE). The real file was used only for manual, interactive verification during development (see above) and is never read by the committed test suite.

**Scope cut**: `exportExt.pdb` (the "My Tag" sidecar table format) is not implemented — out of scope per issue #134's own conservative-scoping instruction, and genuinely a different row-type set (`tag_row`/`tag_track_row`) the Kaitai spec calls out separately. Track color, cue points, and artwork paths are also not exposed on `RekordboxTrack` (straightforward to add later following the same offset-table pattern, just not included in this first pass).

### `library/traktor_library.py` — Traktor `collection.nml` read support (issue #130)

A completely different Traktor file from `software/traktor/README.md`'s `.tsi` *MIDI controller mapping* format — this one is Traktor's *track collection* (tracks + playlists), confirmed against the maintainer's real `/Users/guillain/Music/_Traktor/collection.nml` (Traktor Pro 4, `NML VERSION="20"`, 44,564 `<COLLECTION><ENTRY>` elements) read-only (never written to, per this initiative's standing rule).

Confirmed real shape: each `<ENTRY TITLE="..." ARTIST="...">` holds a `<LOCATION DIR="..." FILE="..." VOLUME="..."/>` (Traktor's own path encoding — `DIR`/`FILE` use `"/:"` as the path-component separator, a holdover from classic Mac OS `:`-separated paths), an `<INFO KEY="7m" .../>` (a human-readable Camelot/Open-Key-style string), a `<TEMPO BPM="..." .../>`, and a `<MUSICAL_KEY VALUE="15"/>` (Traktor's internal numeric key code, independent of `INFO`'s display string). After `</COLLECTION>` there is a top-level `<PLAYLISTS>` section: a `<NODE TYPE="FOLDER" NAME="$ROOT">` containing `<SUBNODES>` of either `<NODE TYPE="SMARTLIST">` (a saved search query, e.g. `$RATING == 5` — no explicit track list) or `<NODE TYPE="PLAYLIST">` wrapping a `<PLAYLIST ENTRIES="N">` of `<ENTRY><PRIMARYKEY TYPE="TRACK" KEY="..."/></ENTRY>` — that `KEY` is exactly `VOLUME + DIR + FILE` concatenated verbatim, which is how a playlist entry joins back to a collection track (verified byte-for-byte against the real file).

`parse_collection(path)` streams the file with `xml.etree.ElementTree.iterparse` (`events=("end",)`), calling `.clear()` on each `<ENTRY>` right after building its `NmlTrack` — this is necessary, not cosmetic, at 44,564 real entries: verified end-to-end against the real file (~0.5s, ~61MB peak RSS, vs. a full `ET.parse`/`fromstring` load of the whole tree). `NmlTrack` carries `title`/`artist`/`location`/`key`/`bpm`/`musical_key` (the `INFO` display string)/`musical_key_value` (the numeric code)/`album`/`volume`; `location` is `DIR+FILE` with `"/:"` swapped for `"/"` but **without** the volume prefixed — this project has no reliable way to know how a given `VOLUME` is actually mounted (the maintainer's real file only ever uses one, `"Macintosh HD"`, the boot volume, which mounts at `/` rather than a guessable `/Volumes/<name>`), so guessing was avoided; `key` keeps the raw, unambiguous `VOLUME+DIR+FILE` string instead, since that's what actually joins to a playlist entry.

`parse_playlists(path)` also uses `iterparse`, `.clear()`-ing every `COLLECTION/ENTRY` it passes over the same way (so this function is equally memory-bounded on the real file despite `<PLAYLISTS>` sitting after the large `<COLLECTION>` section) and then, once the small `<PLAYLISTS>` element itself closes, walking its already-fully-built subtree with `.iter("NODE")` to collect every `TYPE="PLAYLIST"` node's name → ordered list of `PRIMARYKEY` `KEY` strings (a plain `.iter()` walk handles folder nesting at any depth for free, though the maintainer's real file only nests one level deep) — `TYPE="SMARTLIST"` nodes are skipped since they carry no track list to read. Verified against the real file's `<PLAYLISTS>` section (6 real playlists, e.g. `"Spotifion"` with 192 entries; 3 smartlists correctly excluded).

Writing a playlist back out followed in `v0.48.27` as a **standalone single-playlist `.nml`** (for Traktor's *Import Playlist*), never a write into a real `collection.nml`: `build_playlist_nml`/`write_playlist_nml(path, name, [NmlExportTrack])` copy the shape of the `.nml` files Traktor Pro 4 itself writes for one playlist (its `History/*.nml`, checked read-only) — `HEAD`, a `COLLECTION` with one `ENTRY` per distinct track (`TITLE`/`ARTIST` + `LOCATION DIR/FILE/VOLUME/VOLUMEID`, `VOLUMEID` = volume name as in all 44,564 real entries), empty `SETS`, `PLAYLISTS/$ROOT` with one `TYPE="LIST"` playlist (32-hex `UUID`), `INDEXING`; nothing Traktor computes (`AUDIO_ID`, analysis, cues) is fabricated. `workspace.traktor_location(path)` is the inverse of `traktor_key_to_path`: `/Volumes/<name>/…` → that volume, any other POSIX path → `boot_volume_name()` (the `/Volumes` entry symlinked to `/`, `"Macintosh HD"` here), a Windows drive → `"C:"` (unverified); `export_traktor_playlist(..., db=)` fills titles/artists from the metadata cache. Verified by re-exporting every real playlist of the maintainer's `collection.nml` to a scratch directory: 219/219 `PRIMARYKEY`s byte-identical to the originals. Not yet verified: an actual import inside Traktor. The Music Library tab's *Export as Traktor playlist…* button drives it. `tests/test_traktor_library.py` uses a small, hand-written synthetic fixture (3 entries, 1 real playlist, 1 smartlist) matching this confirmed shape — never a copy of the real file, which is 51.7MB of the maintainer's personal library data and stays out of the repo entirely.

### `library/analysis.py` — BPM/Camelot-key analysis (issue #128)

`to_camelot(musical_key)` is a pure, dependency-free lookup mapping standard musical-key notation to the Camelot wheel (e.g. `Am` -> `8A`, `G` -> `9B`) — the practical notation for judging mixing compatibility. Issue #128's real-collection investigation found tracks already tagged in three different notations, so it accepts all three rather than assuming one: plain note names with an optional `#`/`b` accidental and an optional `m`/`min`/`minor` suffix for minor (`F#m`, `Ebm`, bare `G` for major), Open Key notation (Mixed In Key's alternative numbering, e.g. `7m`) via a fixed offset from Camelot's own numbering, and Camelot codes themselves passed straight through/normalized (`8b` -> `8B`) so a caller doesn't need to know which notation a given tag is already in. Unrecognized input returns `None` rather than guessing. A minor key's Camelot number is derived from its relative major (3 semitones up), not hardcoded twice, since that's the actual music-theory relationship the wheel encodes.

`estimate_bpm`/`estimate_key` fall back to audio analysis (via `librosa`) only for files with no existing tag — per the issue's own investigation finding that the maintainer's real files are almost all already tagged, so this is a gap-filler, not a bulk re-analysis pass. `librosa` is gated behind an optional `analysis` extra (`[project.optional-dependencies]` in `pyproject.toml`, install via `uv sync --extra analysis` or `pip install djmidi[analysis]`) rather than a base dependency: it pulls in 18 transitive packages (`numpy`, `scipy`, `scikit-learn`, `numba`, `llvmlite`, `soundfile`, ...), a real weight increase for what's otherwise a lightweight PySide6 + MIDI app, and `numba`/`llvmlite`'s JIT compilation is a known `PyInstaller`-bundling risk for a project that ships release builds, not source. The import is guarded (`try/except ImportError`, module-level `librosa = None` on failure) so the rest of the app — including the base test suite — works with the extra absent; `estimate_bpm`/`estimate_key` raise a clear `RuntimeError` naming the extra only when actually called without it installed. `resolve_bpm_key(existing_bpm, existing_key, audio_path)` is the small helper that prefers whatever's already there and only calls into audio analysis for a missing value, and only when `librosa` is importable — a no-op passthrough otherwise, so a caller doesn't need its own availability check. `estimate_bpm` uses `librosa.beat.beat_track` (issue's own feasibility note: high confidence for steady-beat electronic genres). `estimate_key` uses standard Krumhansl-Schmuckler chroma-profile correlation (`librosa.feature.chroma_cqt`) — shipped rather than deferred, since it's a well-established textbook technique, but the issue's own confidence caveat (chroma-based key estimation commonly runs 70-90% accurate, worse with heavy bass/kick content) means callers must keep it user-correctable rather than silently trusted, same as the issue's proposed scope requires. Tests (`tests/test_library_analysis.py`) generate a synthetic click-track WAV (`numpy`/`soundfile`, no real file from `/Users/guillain/Music` ever touched) and gate every `librosa`-dependent test behind `pytest.importorskip("librosa")` so the suite stays green without the optional extra; the Camelot-mapping tests need no audio and cover every notation found in the issue's investigation comment plus all 24 major/minor keys.

**Background analysis** (issue #224, `v0.48.77`): the Music Library tab's `Analyse BPM/key` button runs `workspace.iter_analyse_missing(db, analyser=None)` as a normal tab job (one track per `next()`, i.e. per 25 ms timer slice — a track is one uninterruptible step on the GUI thread, which is why `analysis.analyse_clip` decodes only a 60 s clip from the middle, once for both estimates). Targets come from `LibraryDB.tracks_needing_analysis()` (present tracks whose *current* cached tags lack a BPM or a non-blank key and that have no `analysis_suggestions` row at the file's current mtime). Results live only in the new `analysis_suggestions` table (`track_id`, `mtime`, `bpm`, `key`; an all-NULL row records a failed/empty attempt so it isn't retried), surfaced as `LibraryRow.bpm_suggestion`/`key_suggestion` (only while the tag is still empty) and drawn amber/italic as `? value` in the BPM/Key/Camelot cells. A file changed outside the app drops its estimate (mtime mismatch); `refresh_track_metadata` calls `carry_analysis_suggestion` after this app's own tag writes so an applied estimate comes back on undo. Files are written only by `Apply analysis suggestions…` → `workspace.analysis_tag_changes` (empty tags only) → the existing `WriteTracksMetadataCommand`. The button is disabled with the reason as tooltip when `analysis.analysis_available()` is false; it turns into `Stop analysis` while running (stopping keeps what was committed — one commit per track). Tests inject a stub `analyser`, so none need librosa.

### MIDI round-trip latency (`midi_latency.py` + `gui/midi_latency_dialog.py`, issue #255)

`View → MIDI Latency Test…` (`MainWindow._on_midi_latency_test`, one non-modal `MidiLatencyDialog` kept on `_latency_dialog`) sends N Note Ons to an output and times the matching Note On on an input. Qt-free core: `LatencyProbe(send, receive, LatencyConfig, clock=)` is a step-wise state machine (one `step()` per poll; injected `send(channel, note, velocity, note_on)` / `receive() -> [MidiEvent]` / `clock`), `run_probe` drives it with an injectable `sleep`, `compute_stats` gives min/median/max/mean and jitter (mean absolute difference of consecutive RTTs), `open_port_pair` adapts real mido ports. A reply is an input-direction `Note On`, velocity > 0, same channel/note; each ping carries its own velocity (`ping_velocity`: 1..127 cycling) and must get it back unless `match_velocity` is off, so a late echo of a timed-out ping never answers the next one. A Note Off follows every ping (its echo is never counted). The dialog runs `run_probe` on a daemon thread (a QTimer's granularity would be added to every RTT) and drains a `queue.Queue` on a 50 ms timer; port factory and thread start are injectable (tests run it synchronously with a fake echo pair). It always says the number is only meaningful with something that echoes (IAC/virtual loopback, MIDI thru, a controller known to echo LEDs) — no controller echo behaviour is assumed or recorded.

**Controller triggers** (issue #252, MIDI Learn for macros): `MidiMacro.trigger` is an optional `MacroTrigger(event_type, channel, data1, port)` — only `"Note On"`/`"Control Change"`, learned via `midi_learn.trigger_from_event` (a press only) plus the event's input port, so the same note on two controllers stays two triggers; a blank `port` matches any input, and ports compare case/punctuation-insensitively. Written to the macro's JSON only when set (old files keep their shape). `macros_for_event` finds the macros a live press fires; `validate_macros` also refuses two macros on overlapping triggers and `retriggers_itself` (trigger port == output port and a step re-sends the trigger as a press — a loopback port would loop forever). The dialog's Trigger row (`Learn`/`Clear`, `LEARN_TIMEOUT_MS`) opens no port: `MacroManagerDialog(ensure_listening=MainWindow._ensure_learn_listening)`, and while it is open `MainWindow._macro_dialog` gets every live event via `feed_learn_event` and no macro fires; otherwise `_on_live_midi_event` plays `_play_triggered_macros` unless the edit panel's Learn consumed the event. `_ensure_macro_triggers_listening` (real-app startup, and after Manage Macros OK) auto-starts the Live Monitor when a macro has a trigger and `auto_start_live_monitor` is on. A triggered macro plays alongside whatever the DJ software maps that button to — the app can't intercept the press.

### `library/playlist.py` — BPM/key/genre-aware playlist generation (issue #131)

The "simple filter+sort" mode from issue #131's proposed scope: `PlaylistTrack` (`identifier`/`category`/`bpm`/`camelot_key`) is a deliberately minimal, decoupled dataclass — not tied to `LibraryDB`, #127's `Category`, or #128's analysis output types — so this module builds against whatever those already produce without depending on #127/#129 merging first (the caller resolves a taxonomy category and a Camelot key, then passes plain values in). `is_camelot_compatible(a, b)` implements the standard harmonic-mixing rule (same key, +/-1 on the wheel for an energy change, or same number/other letter for the relative major/minor) via a small parsed-Camelot-code comparison; `is_bpm_compatible(a, b, tolerance_pct=6.0)` checks a percentage window rather than a fixed BPM delta, per the maintainer's own framing ("un trop gros écart est rédhibitoire, sur les BPM" — a proportional gap matters more than an absolute one across the wide BPM range this library spans, tek/hardcore easily running 180+ against reggae/dub's 80s). `find_compatible_tracks(seed, candidates)` returns compatible candidates sorted by BPM closeness, excluding the seed itself and anything with a missing BPM or an incompatible key/category.

`build_playlist_draft(tracks)` implements the maintainer's explicit default ordering for a generated playlist, given verbatim in-session: *"Groupé par catégorie, puis par range de BPM, puis trié par clef"* — category first, then a `bpm_bucket()` grouping (tracks within `bpm_bucket_width` BPM of each other land in the same bucket rather than needing an exact match), then sorted by Camelot key string within that bucket. Tracks missing a category/BPM/key sort last within their group rather than being silently dropped, so an incomplete tag doesn't just vanish from the draft.

The harder "full ordered-path" mode followed in `v0.48.63` (issue #191): `build_playlist_path(tracks, start=None, *, tolerance_pct, direction="up"|"down"|"flat", max_length=None)` → `PathResult(path, leftovers)`. Every adjacent pair is BPM- and Camelot-compatible and the BPM never moves against `direction` (equal BPM is allowed both ways); default start is the slowest track (fastest for `"down"`). It is a **receding-horizon** beam search (beam 8, lookahead 3, commit one move per step) rather than a whole-path beam, which would copy a used-set per state per step; candidates come from `_PathIndex` (BPM-sorted lists per Camelot key, scanned outwards from the current BPM, at most `beam_width // 2` per key and side, committed tracks deleted), so 3,000 tracks take well under a second. Step cost = BPM move in % + key step (same 0 / ±1 1 / relative 1.5) + category change (2, unknown 1); a continuation that dead-ends inside the window costs 100 per missing step. Ties break on the identifier, so it's deterministic. Tracks with no BPM/key or unreachable go to `leftovers` (simple-mode order), never dropped. `workspace.generate_playlist_path` wraps it; the Music Library's `Auto: mix path…` asks the direction, starts from the current row when it has BPM+key, and writes the path plus a separate `"<name> (leftovers)"` playlist. Simple mode stays the default (`generate_playlist` unchanged). `v0.48.69` (issue #211) replaced the direction-only `QInputDialog` with `MixPathDialog` (direction, BPM tolerance ±0.5–20 %, maximum length with 0 = `No limit`, plus a "current filter only" note naming the visible-track count); `generate_playlist_path` gained `max_length`. The last choices are a `workspace.MixPathOptions` (`normalized()` clamps anything stale back into range) saved by `save_mix_path_options` in a new `library_settings` key/JSON-value table of `LibraryDB` (`get_setting`/`set_setting`) — kept in the library index rather than `preferences.json`, so the test suite's `:memory:` index never sees the real values.

### `taxonomy/` — genre/style taxonomy and alias normalization (issue #127)

A plugin-style registry package mirroring `catalog/`'s pattern (`taxonomy/_registry.py` holds the `Category`/`CategoryMatch` dataclasses and a plain-dict registry, one module per top-level genre family — `tek.py`, `electro.py` — registers itself on import, `taxonomy/__init__.py` discovers every non-underscore module in the package via `pkgutil` and re-exports the public API). A `Category` is `(family, name, aliases)` — a two-level `Family%%Name` pairing matching the maintainer's own real Serato Subcrate naming convention (`_Serato_/Subcrates/*.crate`), seeded directly from the real, mined counts in issue #127's investigation comment: `Tek` (Tribe ×24, HardTek ×22, RaggaTek ×17, HardCore ×10, FrenchCore ×9, PsyTrance ×6, BarBass ×6) and `Electro` (Drum & Bass ×8, Dub ×8, DnB_jungle_pungle ×6, Ragga Jungle ×3, Break beat ×2) — `DnB_jungle_pungle` is deliberately its own category, not folded into "Drum & Bass", since the maintainer's real crates keep that jungle-flavored fusion separate. Aliases seeded per the maintainer's explicit federation list: Drum & Bass ↔ DnB/D&B/Drum and Bass; PsyTrance ↔ Psy/Psytrance/Psy-Trance; Tribe ↔ TribeTek/Tribecore; RaggaTek ↔ Raggatek/Reggaeton Tek/Ragga Tek.

`resolve_category(raw_genre, folder_hint=None, crate_hint=None)` is the entry point, and takes all three because the investigation found the raw `TCON` tag alone is often unreliable — real tracks filed by hand under `Tek/PsyTrance` carry `TCON` values like `House`/`Techno`/`Other` — so it tries an exact/alias match against `crate_hint` first, then `folder_hint`, then `raw_genre`, splitting a hierarchical hint on `%%`/`/`/`>` (a crate's trailing playlist-name segment, e.g. `Tek%%PsyTrance%%SomePlaylist`, is ignored — only the first two segments matter) and falling back to a bare subcategory-name/alias match if the family segment isn't recognized. Returns a `CategoryMatch(category, confidence, score, matched_text, source)`, `confidence` one of `"exact"`/`"alias"`/`"fuzzy"`/`"none"`. Only when no candidate produces an exact/alias hit does it fall back to `rapidfuzz` (`fuzz.WRatio`, threshold `FUZZY_THRESHOLD = 70.0`) across every category's name/canonical/aliases, and that result is always `confidence="fuzzy"` — a suggestion only, **never** silently auto-applied, per the maintainer's hard requirement (they want near-synonyms federated, but always with confirmation). `merge_categories(keep, absorb)` folds one category's name+aliases into another's and removes it from the registry (for a maintainer-confirmed duplicate); `add_alias(canonical, alias)` federates one more spelling into an existing category. Both are in-memory only, like `catalog/`'s `register(..., replace=True)` — persistence is a future GUI's job, not this issue's.
### `library/serato_library.py` — Serato crate (playlist) format

Issue #129's first slice: read/write for `_Serato_/Subcrates/*.crate` playlist files only — **not** `database V2` (the main library index), which stays unimplemented/out of scope by design per the issue's own risk framing (a bad write there risks corrupting the whole real library, not one playlist). Named `serato_library.py`, not `serato.py`, to avoid colliding with the pre-existing `src/djmidi/software/serato.py`, which is about something unrelated (MIDI *controller mapping* XML).

Both `database V2` and a `.crate` file share the same on-disk shape, confirmed by reading (never writing) the maintainer's real `_Serato_` folder: a flat stream of chunks, each a 4-character ASCII tag, a 4-byte **big-endian** uint32 length, then that many bytes of value. `iter_chunks(data)` is the Qt-free, defensive low-level reader (mirroring `parser.py`'s XML defensiveness) — an unrecognized or nested tag is yielded like any other rather than raised on, and a chunk whose declared length runs past the end of the buffer stops the scan with a logged warning instead of raising, since the crate schema beyond `vrsn`/`otrk`/`ptrk`/the `osrt`/`ovct` column-definition chunks isn't fully documented. `write_chunk`/`write_chunks` are the corresponding assembler. `parse_crate(path)` walks the top level for `otrk` chunks and pulls each one's nested `ptrk` (a UTF-16BE relative file path, e.g. `"Users/guillain/Music/Tek/..."`), skipping any other sibling chunk (`osrt`/`ovct` column-display settings, or anything else) — this was cross-checked read-only against all real `.crate` files currently in the maintainer's `_Serato_/Subcrates/` (213 files, 25,538 tracks parsed, zero failures), never written to. `write_crate(track_paths)` builds a new stream from scratch containing just a `vrsn` header (`"1.0/Serato ScratchLive Crate"`, matching what real crates carry) plus one `otrk`/`ptrk` pair per path — the `osrt`/`ovct` column-definition chunks real crates also carry are display-only preferences Serato regenerates on its own, so they're deliberately omitted rather than fabricated; `write_crate_file(path, track_paths)` writes those bytes to exactly the path the caller passes and never searches for or touches an existing crate on its own initiative. `tests/test_serato_library.py` is the committed round-trip test (`write_crate` → `parse_crate` on synthetic, made-up paths) — no real crate bytes or paths are committed to the repo, per the personal-library-data concern in issue #129.

### Relinking missing tracks (`library/relink.py`, issue #190)

A scan flags a moved file's old row `missing` and indexes the new path separately. `iter_relink_proposals(db)` (generator, drained by `find_relink_proposals`; the Music Library tab runs it as a timer job) ranks candidates per missing track — present indexed tracks plus, with `search_roots`, unindexed audio files under the roots whose name matches — as `name+size` > `name` > `tags` (same cached title+artist, casefold), with `tags_agree` as a tie-breaker; `confident` = exactly one `name+size` candidate that no other missing track also confidently claims. `apply_relinks` skips a candidate that vanished or lies outside every root, then `LibraryDB.relink_tracks` applies all links in one transaction: an already-indexed target absorbs the old row (playlist paths rewritten, cached tags moved only if the target has none, stale row deleted), otherwise the missing row itself takes the new path. `RelinkDialog` in `music_library_view.py` reviews the proposals (opened via `QTimer.singleShot` after the job stops, so the modal loop can't re-enter the generator). ### Duplicate track detection (`library/duplicates.py` + `gui/duplicates_dialog.py`, issue #184)

Qt-free, read-only, two tiers. **Metadata**: `metadata_key(artist, title)` = `normalize_artist`/`normalize_title` (NFKD + accents dropped, casefold, `feat.`/`ft.`/`featuring` credit dropped, title-only `(Original Mix)`/`(Original)`/`(Original Version)`/`- Original Mix` dropped, every other version marker such as `(Extended Mix)`/`(Radio Edit)`/remixes kept, non-alphanumeric runs → one space; rules in the module docstring), `None` when either side is empty so untagged tracks never group; `find_metadata_duplicates` works off the tag cache (`metadata_entries(db)`). **Exact**: `iter_exact_duplicates((path, size))` only opens files whose DB size another file shares (`exact_candidate_count` = its progress total), groups them by a `PREFIX_BYTES` hash, then a full chunked `blake2b` for files larger than the prefix; it yields after every chunk (a huge WAV can't stall a slice) and returns the groups via `StopIteration.value`, like `scanner.iter_scan_root`; unreadable files are logged and skipped, empty files ignored. `MusicLibraryView.find_duplicates()` runs both on the existing `_start_job`/`QTimer` slicer and opens a non-modal `DuplicatesDialog` (`self.duplicates_dialog`): tier → group → file tree with format/size, bitrate read lazily on group expand (`audio_bitrate`, mutagen stream header only), Reveal in Finder via `file_reveal`. Duration isn't compared (the tag cache doesn't hold it).

**Version suggestions** (issue #257): a third tier, `TIER_VERSIONS`, from `find_version_variants(entries)` — `song_key(artist, title)` = `normalize_artist` + `song_title` (feat. stripped, then `strip_version_markers` peels trailing `(…)`/`[…]` groups or a spaced ` - …` suffix one at a time while one of its words is in `VERSION_WORDS` — edit/mix/remix/extended/radio/remaster(ed)/original/vip/dub/live/… — never leaving an empty title, so `(Part 2)` stays). A group is kept only with ≥2 distinct `metadata_key`s (two copies of one radio edit are the metadata tier's job); `DuplicateGroup.variants` carries each path's own title. **Discarding copies** (`library/discard.py`, issue #208): file rows are checkable (one tick per path, mirrored across an exact and a metadata group listing the same file); `Move ticked to Trash…` emits `DuplicatesDialog.discardRequested(paths)` → `MusicLibraryView.discard_duplicates`. ### Change history (`library/change_log.py` + `gui/change_history_dialog.py`, issue #261)

Every write this app makes to a real file is logged in `LibraryDB` (`change_log` = one row per operation, `change_items` = one row per file with before/after JSON; `add_change`/`list_changes`/`get_change`/`mark_change_reverted`/`prune_changes`, kept to `MAX_ENTRIES` = 1000), because the tab's `QUndoStack` dies with the session. Hooked up in #279: `WriteTrackCoverCommand` takes an optional `recorder(summary, path, old, new)` and `RenameFilesCommand` a `recorder(summary, pairs)`, both called on every redo/undo pass (renames: only the pairs that pass actually renamed; nothing when nothing was), wired by `MusicLibraryView._record_cover_change` → `change_log.record_cover_change` and `_record_renames` → `record_renames`. ### Traktor `.tsi` controller mappings (`software/_tsi.py` + `binary_chunks.py`, issue #122)

The `traktor` software plugin now reads the real Traktor controller-mapping format: a `.tsi` is settings XML (`<NIXML>`) whose `DeviceIO.Config.Controller` entry holds a Base64 blob of nested "4-char tag + u32 BE size" chunks (layout, sources and the real-file verification table in `software/traktor/README.md`). `binary_chunks.py` is a **format-agnostic** codec for that framing (`decode(data, ContainerSpec)` → `ChunkNode` tree, `encode` recomputes every size; which chunks are containers, and the fixed header before their children, is passed in keyed by `(parent_tag, tag)` because Traktor's `DCBM` is a list under `DDCB` but a leaf inside it) — written generic on purpose, per the maintainer's "approche générique" instruction, so a future binary-in-XML format (Serato's crate framing is the same shape) reuses it. `_tsi.py` (underscore-prefixed so `software.discover_plugins` doesn't import it as a plugin) builds `TsiDocument` → `TsiDevice` → `TsiMapping` on top; `traktor.parse_string` turns every MIDI-bound mapping into one `Control` (`extra_attrs` `tsi_device`/`tsi_binding`/`tsi_label` locate it in the blob; its one `UserIO` is `click` for input, `output` for LED feedback; `MappingElement.tag` is the command name) and stashes the `TsiDocument` on the config object (`_tsi_document` attribute, not `extra_attrs`, which is `dict[str, str]` and would drag a multi-megabyte string through every consumer).

Everything was verified on the four real exports in `data/traktor/*.tsi.zip` (9,360 mappings): unmodified tree + Base64 re-encode byte-identically; note naming is `C-1` = 0, cross-checked against the official Pioneer values in `catalog/xdj_xz.py` (Traktor's own XDJ-XZ mapping has Play/Cue/Sync on notes 0/1/31, same as Pioneer's MIDI list — which also confirms command IDs 100/206/125, the only three named in `COMMAND_NAMES`); two real cases the community spec doesn't mention are handled — a mapping with **no binding** (command never MIDI-learned: kept in the file, skipped in the views) and **compound labels** (`Ch01.CC.032+Ch01.CC.000`: shown by their first part, never rewritten). Export is deliberately narrow: `_export_tsi` only re-labels bindings whose trigger changed, on a `deepcopy` of the tree so the source document stays pristine (an undone edit or cancelled save can't leave a stale label behind); adding/removing bindings, rewriting a compound binding, or an unsupported event type raises `TsiError` rather than synthesizing `CMAD` payloads whose unknown fields aren't understood. An unedited export is byte-identical to the input file. The legacy flat `<NML><MAPPINGS>` path is kept only so files this app produced earlier still open — it was never a real Traktor format.

Saving a `.tsi` goes through the normal `safe_update.prepare_update`, which gained two generic things for this: diff lines longer than `MAX_DIFF_LINE` are elided in the preview (never in the written file), and an optional `summarize(old_text, new_text)` callback — fed from the new optional `SoftwareDefinition.change_summary` field, `_tsi.describe_changes` for Traktor — is prepended, so the confirmation lists re-assigned bindings instead of a 5 MB Base64 line. Real-app check: the 8,963-mapping XDJ-XZ export loads into `MainWindow` in ~0.6 s and exports + re-validates in ~0.5 s. That file spans 10 MIDI channels, which exposed a layout limit: the By Channel/Deck/Controller column rows now sit in a horizontal `QScrollArea` (`splitter_utils.scrollable_columns`; `replace_splitter` accepts the scroll area as its container) and each tree column has `MAPPING_COLUMN_MIN_WIDTH` (220 px) — few columns still stretch to fill the width, many columns scroll sideways instead of truncating every row.

**Serato ↔ Traktor conversion (issue #194) is research-only, deliberately not implemented.** The Traktor half (re-labelling a template `.tsi`'s existing bindings; `CMAD.TargetDeck` 0-3 = decks A-D; commands 100/206/125 now also confirmed on the CMD Micro and CMD Studio 4a catalogs) is ready, but none of the three real Serato exports contains a Play/Cue/Sync element (only `auto_loop_specific_length`, `auto_loop_roll_specific_length`, `codfather_st`, `codfather_fx`), so Serato's tag names for them are unknown and neither direction can be built without inventing them. `software/traktor/README.md`'s "Serato ↔ Traktor conversion: research" section has the evidence, the `CMAD` unknown-field findings, and the exact captures that would unblock it — don't ship a converter before those exist.

Maintainer-chosen rule: one photo at a time (Controller/MIDI exclude each other, both may be off) and Layout greyed out while MIDI shows, because `CONTROL_GEOMETRY` was measured on the clean photo and the `-midi` pictures are different crops. A view calls `set_available(photo=, midi=, layout=)` for the controller it shows and draws `state()` (ticked ∧ available; a ticked-but-unavailable MIDI falls back to the photo). Controller Images keeps both pixmaps in its scene and only toggles visibility (`_apply_layers`), so a toggle keeps the zoom and live state; the By… views and `EmulatorLayoutView.set_layers` rebuild, drawing `layout_view.draw_midi_photo` alone for MIDI and skipping the markers when Layout is off. Photo layers are only offered there in real-position mode.

### Reverse function search (`function_search.py`, `gui/function_search_view.py`, issue #185)

"Which control triggers function X?". `function_search.index_functions(config)` (Qt-free) builds one `FunctionResult` per `(tag, userio event, deck_id, slot_id)` with its distinct `Trigger`s (the 10x duplicates collapse), the first `Control` per trigger and every `MappingElement`; `search_functions(config_or_index, query)` tokenizes the query (lowercase alphanumerics), lifts `deck N`/`slot N` into exact id constraints and `click`/`press`/`output`/`led` into an event filter, then requires every remaining token to hit a tag word (exact 3 > prefix 2), a deck/slot id (bare number, 1) or a substring of the joined tag (1), plus a phrase bonus; ties sort click before output, then tag, deck, slot. Ids are shown raw (`Deck 0`), matching the By Deck tab. `FunctionSearchView` sits at the top of `_right_splitter` (one instance for the three mapping tabs, results list hidden until something matches, two-line word-wrapped rows because that column is ~170-450 px wide); `MainWindow._on_function_result_selected` selects the first control in the current tab (By Deck: `_select_deck_group_for_mappings`, the exact deck/slot row; By Controller: `_select_controller_cell` then the exact control in the channel columns so the edit panel shows it; otherwise/unresolved: By Channel), then calls `set_selected_keys` with the union of every trigger's presentation keys *after* the tree selection, whose own handler narrows it to one control. The edit panel now sits in an `AutoSizeScrollArea` (`_edit_panel_scroll`) since its ~850 px minimum height overlapped itself in that column at 1100x700.

### Readable function names (`function_names.py`, issue #209)

Qt-free `FUNCTION_NAMES` table: raw Serato tag → short label, limited to the four tags the real exports in `data/` contain (`test_function_names.py` asserts the table equals that inventory, so adding a name for a tag no real file carries fails). Labels come only from the tag's own words — `codfather_st`/`codfather_fx` are just re-cased since their meaning was never confirmed, and a slot stays `· slot N` because slot→loop-length isn't documented. Unknown tags (Traktor command names included) fall back to the raw tag. Consumers: `tree_model.mapping_label` (+ `MappingFilterProxy`, so the By Channel filter still matches a raw tag), `deck_tree`/`controller_tree` leaves (raw tag in tooltips), `FunctionResult.label` (readable words are searchable too), `mapping_diff.function_label` (entries keep `old_raw`/`new_raw` for the dialog tooltip; sorting stays on raw labels) and `cheat_sheet.function_text` plus a trailing `Function names` glossary sheet (`glossary_sheet`). The raw tag must stay visible wherever a label replaces it.

### Layer Map (`gui/layer_map.py` + `gui/layer_map_dialog.py`, issue #253)

`View → Layer Map…` opens a non-modal, read-only table for one controller: a row per `layout.cell_key` cell (every deck's copy of a pad collapses to one `Pad N` row, a button to one row with its SHIFT/long-press variants), a column per layer. The Qt-free `build_layer_map(config, controller)` derives layers from `layout.reverse_lookup()` variant names only — the pad bank in parentheses (`cheat_sheet._BANK_RE`), a SHIFT marker, or the qualifier `layout._base_name()` strips — so no layer exists unless the catalog names a trigger for it; `is_shift` ignores the bank's own text, because DDJ-1000/FLX10/800 have a `KEY SHIFT` pad mode (since `v0.48.105`, issue #280, that rule is `cheat_sheet.is_shift`, shared by both modules: the cheat sheet's `_is_plain`/SHIFT split strips the bank too, so a KEY SHIFT pad is no longer printed as a `SHIFT:` line). Since `v0.48.108` (issue #288) the rule itself lives in `gui/layout.py` (`PAD_BANK_RE`, `name_without_bank`, `is_shift_variant`, `is_plain_variant`; `cheat_sheet._BANK_RE`/`is_shift`/`_is_plain` are aliases) so `layout.pick_default_variant` applies it too: with SHIFT latched, the Controller Emulator no longer picks a plain `KEY SHIFT` pad variant as the SHIFT one. Cells resolve through `cheat_sheet.build_function_index` (input/`click` elements only, 10x duplicates collapsed); a cell is `free` when none of its raw triggers is bound, `partial` when only some channels are (e.g. a pad mapped on deck 1 only) — `free_triggers` names what's left. `MIDI-OUT` (LED-only) sections are excluded. The dialog lists `cheat_sheet.candidate_controllers` first, then every other registered controller, and re-reads the mapping through a `config_provider` callable on *Refresh*.
### Command palette (`command_palette.py`, `gui/command_palette.py`, issue #222)

`View → Command Palette...` (`Ctrl+K` = Cmd+K on macOS, `ApplicationShortcut` so it works from floating docks) opens `CommandPaletteDialog`, a keyboard-only popup (the field keeps focus; Up/Down/PageUp/PageDown move, Enter runs, Esc closes) over a Qt-free `PaletteIndex`. Ranking lives in `command_palette.py`: every token must match; exact title word > word prefix > substring > in-order subsequence of the title (`opmap`), keywords (menu path, album/file name) at 0.75x, a phrase bonus mirroring `function_search`'s so scores are comparable, and kind order (action, tab, function, track) breaks ties. Functions are not re-scored: `search_functions` over `FunctionSearchView._index` is merged in as-is. Tracks need `TRACK_MIN_QUERY` (2) characters and skip the subsequence fallback (noise and cost over ~85k rows). `MainWindow._palette_index` collects entries on each open: `gui.command_palette.menu_entries` walks the menu bar (enabled visible leaves only, `clean_menu_text` strips mnemonics/ellipses, checkables get `(on)`/`(off)`, the palette's own action skipped), one entry per `left_tabs` tab, and `_palette_track_entries` from `music_library_view.table_model._rows` -- only when the library DB is already open (the palette never opens it) and cached by the rows list's identity. `open_command_palette` uses `open()` not `exec()` so tests drive it; `_run_palette_entry` triggers the QAction / switches tab / calls `_on_function_result_selected` / selects the track (clearing library filters if one hides it).

### Startup timing and lazy loading (`startup_timing.py`, issue #264)

`djmidi.main()` calls `startup_timing.begin()` before importing the GUI; `gui.app.run()` takes that timer (`take()`, a fresh one when launched another way), marks `imports` / `preferences and logging` / `Qt application` / `main window built` / `window shown`, and a `QTimer.singleShot(0)` logs `Startup: time to first window … ms -- <per-phase breakdown>` once the window paints. Two deferrals cut `MainWindow()` from ~0.78 s to ~0.48 s: `IntroductionView` keeps each card photo in `_pending_card_images` until its card is current (`_load_card_image`), and `LiveSendControl(defer_port_scan=True)` (used by `ControllerLayoutView` and `ControllerImageView`, not the emulator, which is shown on creation) lists output ports on first `showEvent` or `selected_port()`. Tab widgets themselves stay eager on purpose: `_on_live_midi_event`, selection sync and controller detection call into the By…/Controller Images views whatever tab is current, so their scenes must exist.
### Interface language (`i18n.py`, `gui/translation.py`, issue #263)

Standard Qt translation: user-visible strings are wrapped in `self.tr(...)` (context = the class name), `scripts/update_translations.sh` runs `pyside6-lupdate -no-obsolete -locations none` over its `SOURCES` list into `src/djmidi/translations/djmidi_fr.ts` and `pyside6-lrelease` into the committed `djmidi_fr.qm` (bundled by `scripts/build.sh`). First pass only covers `main_window.py`'s menus/tab titles/corner buttons and `preferences_dialog.py` — a file that gains `tr()` calls must be added to `SOURCES`. The follow-up (`v0.48.106`, issue #281) added the windows built in parallel with it: `first_run_wizard.py` (each `QWizardPage` subclass is its own `tr()` context, e.g. `_ControllersPage`), `live_ready_dialog.py`, `midi_latency_dialog.py`, `layer_map_dialog.py`, and the #256–#261 Music Library pieces (`music_library_view.py`'s cover/statistics/smart-playlist/rename/change-history buttons and `SmartPlaylistDialog`, plus `library_stats_dialog.py`, `rename_files_dialog.py`, `change_history_dialog.py`); text produced by Qt-free modules (live-ready findings, `format_stats`, change-log descriptions) stays English. Placeholders use `self.tr("… {name} …").format(name=…)` (never an f-string inside `tr()`), and `test_i18n.py` checks every French translation keeps the same `{placeholders}`. A widget filtering on its own label (Layer Map's "All sections") must compare by index or data, not by the now-translated text. `self.tr` needs a literal (lupdate can't read a variable), so a module-level label constant is wrapped at its use site instead. `PluginPreferences.language` (`"system"`/`"en"`/`"fr"`, default `"en"`; an unknown value falls back to `"en"` with a warning rather than discarding the file) is resolved by the Qt-free `i18n.resolve_language` and installed by `gui.app.run` → `install_translators` (app catalogue + PySide6's `qtbase_fr`) before `MainWindow` exists, so a change applies at the next launch. Tests never install a translator: the suite always sees English. Code must not match a translated title — Preferences tabs carry their English key as `tabBar().tabData()`, which `_on_preferences(tab=...)` matches. `tests/test_i18n.py` fails on an untranslated wrapped string (re-runs lupdate into a temp copy) or a stale `.qm`.

### Small-window sizing for dialogs (`gui/window_size.py`, issue #282)

Issue #19's rule (nothing clipped or squeezed at small sizes) applied to the separate windows of the v0.48.90–v0.48.103 batch. Three helpers: `fit_to_screen(window, w, h)` replaces a hard-coded `resize()` and caps the default to 92 %×90 % of the available screen (`fit_size` is the Qt-free arithmetic, same ratios as `MainWindow._default_window_size`); `usable_minimum(view, w, h)` gives a table/list/tab widget a floor the layout carries up to the window's minimum; `keep_wrapped_text_visible(window)` fixes a Qt gap — a top-level window's minimum height ignores height-for-width, so at the minimum width a word-wrapped label took the room of the spin boxes/combos beside it (MIDI Latency Test, Smart playlist) or got clipped (Rename files). It installs an event filter that, on every `LayoutRequest`, sets the minimum to `layout.totalMinimumHeightForWidth(min width)` (any minimum the window set before the call stays a floor). `tests/test_small_windows.py` opens every audited window at its default and minimum size and fails on a squeezed button/combo/line edit/spin box, a clipped wrapped label, a table under 80 px, or a minimum larger than 900x600; new dialogs should use these helpers and join that list. Under the offscreen platform the screen is 800x800, so `fit_to_screen` makes those dialogs narrower in tests than on a real display.

Issue #290 re-checked them on the real macOS `cocoa` platform, in English and French (a throwaway script building the windows directly, `QT_QPA_PLATFORM=cocoa`, scratch `DJMIDI_*` paths, application name not set, so no QSettings/Sync). Fixes: a fourth helper `keep_tab_titles_whole(tabs, scroll=True)` (`ElideNone` + scroll arrows) — macOS elides crowded tab titles to "Pa…"/"DD…" — on `left_tabs`, the Dashboard's controller tabs and (with `scroll=False`, so the panel grows inside its scroll area) the Music Library side tabs; shorter French main-tab titles (`Config. contrôleur`, `Images contrôleur`, `Bibliothèque`) and wizard sync checkbox; Layer Map's free-layer checkbox on its own row and its section combo sized for the translated "All sections"; MIDI Latency Test pairs its spin boxes on two rows (one per row needed 617 px of height on macOS); Preferences shows the workspace path in a read-only `QLineEdit` above its buttons (as a label it set a 1118/1243 px minimum width). `test_small_windows.py` re-runs every audited window with the French catalogue installed (`french` fixture). Remaining, not layout: text from Qt-free modules (`midi_latency.ECHO_WARNING`, `library/rename.py`'s relink warning) and most tab contents are still English.

### "Ready for live" check (`live_ready.py`, issue #254)

Qt-free `check_live_ready(config) -> ReadyReport` (findings sorted error → warning → info, each a `ReadyFinding` with `category`, plain-language `message`/`hint`, and the first raw `Control` for navigation), shown by `gui/live_ready_dialog.LiveReadyDialog` from a `Validate` / `Ready for live…` button strip above `issues_table` (now wrapped in `self._validation_area`, the right splitter's third widget) and `Edit → Ready for Live…`. ## What this project is

DJ MIDI Studio: a tool to simplify managing, visualizing, and modifying Serato DJ Pro MIDI configuration files (XML), which can run to 16,000+ lines. Planned capabilities (see README.md):

- **XML Parsing & Modeling**: parse Serato MIDI config XML into a structured object-oriented model (Decks, Channels, Notes, Slots, etc.)
- **Visual Mapping Editor**: GUI to visualize/modify MIDI mappings — object attributes (on/off values, colors) and associated events (Click, Output)
- **Validation**: catch mapping conflicts or invalid XML structure after edits
- **Export**: write a clean, valid XML file re-importable into Serato DJ Pro

## Domain model (Serato MIDI XML format)

`data/xdj_xz-ddj_xp2-4decks.xml` is the user's real, current Serato config (XDJ-XZ/DDJ-XP2, 4 decks) and the best reference for the XML shape — also used as the primary test fixture:

- Root `<midi app="...">` contains a flat list of `<control channel="..." event_type="..." control="...">` elements — these are the raw MIDI trigger (channel/note/control number).
- Each `<control>` holds `<userio event="click">` and/or `<userio event="output">` blocks.
- Inside a `userio` block, one or more mapping elements (tag name = the Serato function, e.g. `codfather_st`, `auto_loop_roll_specific_length`) carry `deck_set`, `deck_id`, `slot_id` attributes.
- Each mapping element contains a `<translation action_on="press|any|..." behaviour="toggle|explicit|...">`, optionally with `<alias name="on|off|selected" value="...">` children mapping logical states to raw MIDI values.

Any XML parsing/modeling code should be validated against this sample file's structure.
